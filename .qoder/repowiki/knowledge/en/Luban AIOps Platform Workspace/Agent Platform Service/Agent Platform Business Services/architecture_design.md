The module is a flat collection of service modules that sit above the runtime kernel and persistence layers. `runtime_service.py` exposes the HTTP-facing entry points (`chat`, `stream_chat`, `live_status`, `ready_status`) and delegates execution to `AgentKernel` obtained via the process-wide singleton in `runtime_dependencies.get_runtime_kernel()`. Session lifecycle (create, get, rename, list, delete) is centralized in `session_service.py`, which enforces ownership checks and coordinates cleanup across multiple stores (`AGENT_STATE_STORE`, `EVIDENCE_STORE`, `CONFIRMATION_RECORD_STORE`, `EXECUTION_RECORD_STORE`). Storage is abstracted by a `SessionStore` Protocol in `session_store.py` with three concrete backends — `InMemorySessionStore`, `RedisSessionStore`, and `PostgresSessionStore` — selected at startup via the `SESSION_STORE_BACKEND` env var through `build_session_store()`, with automatic fallback to memory when Redis or Postgres are unreachable. Cross-cutting kernel behavior is implemented as AgentScope middleware in `kernel_middleware.py`: `GatewayPermissionMiddleware` implements the allow-list permission gate (ASK for unvetted tools, auto-ALLOW for task/structured-output built-ins), and `ToolEvidenceMiddleware` emits SPEC-011 tool_call/tool_result frames into a request-scoped `ContextVar` sink. Model discovery in `model_discovery.py` runs a background loop that resolves provider model series from live `/models` endpoints, falling back through in-memory last-good → Postgres cache → curated series, and atomically swaps the catalog via `model_catalog.refresh_catalog`. Supporting modules handle HITL confirmation records (`hitl_confirmations.py`, `confirmation_records.py`), execution signing/worker client (`execution_signing.py`, `execution_worker_client.py`, `execution_records.py`), audit emission (`audit_emitter.py`), document/prose handling (`document_prose.py`, `operation_documents.py`), shift summaries (`shift_summary.py`), and session transcripts (`session_transcript.py`). Dependency direction is one-way: services depend on `agent_service.runtime_kernel`, `agent_service.providers`, `agent_service.core.*`, and each other only through well-defined singletons; no service imports the FastAPI layer.
