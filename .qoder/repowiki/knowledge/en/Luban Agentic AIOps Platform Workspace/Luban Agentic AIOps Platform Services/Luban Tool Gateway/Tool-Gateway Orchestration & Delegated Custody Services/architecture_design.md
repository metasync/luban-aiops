Two cooperating layers sit under this package:

- Invocation orchestration: `gateway_service.py` is the single entry point (`invoke_tool`, `invoke_delegated`) that resolves identity via `token_verifier`, enforces static + per-tool policy through `policy_engine`, dispatches to `ToolRegistry`, applies redaction, then emits both in-process audit logs and durable events via `audit_emitter`. The shared `_dispatch_invocation` path is also consumed by the private delegated route so both public and execution-runtime paths enforce identical policy.
- SPEC-070 delegated authorization runtime: `authorization_service.py` owns the six `/api/v2/targets/authorizations` handlers. It composes three collaborators — a transaction store (`authorization_transaction_store.py` with `MemoryAuthorizationTransactionStore` and `PostgresAuthorizationTransactionStore`), a durable custody store (`delegated_custody.PostgresCustodyStore`), and an acquisition client (`tools.user_delegated_client`). Browser binding is enforced by `select_browser_secret` / `browser_proof_matches` (cookie jar bounded to 8 UUID-named entries, hashed secret compared against stored hash).
- Trust boundaries: `delegated_invoke.py` independently re-verifies the execution-workload SA token and the two human bearers (requester + approver) against their JWKS, matching them to the signed projection's fields; tokens are never persisted or echoed. `authorization_service.authenticate_authorization_workload` uses a dedicated `luban-target-authorization-handoff` audience distinct from the execution workload audience.
- Persistence primitives: `delegated_custody.py` provides the Postgres-backed credential state machine (`absent → in_flight → staged → active` / revoked), key rotation, recovery epoch fencing, and refresh-token lifecycle. `custody_crypto.py` implements versioned AES-GCM envelopes bound to `(key_id, recovery_epoch, purpose, binding)` with no retained-key fallback. `custody_schema.py` holds DDL and explicit `UPGRADE_V1_TO_V2` / `UPGRADE_V2_TO_V3` migrations. `authorization_transaction_store.py` stores routing state (challenge id, browser proofs, PKCE verifier) in the same `gateway_custody.*` tables as custody, sharing the same `guarded()` connection policy.
- Operator surface: `custody_cli.py` exposes `migrate`, `recover`, `readiness/status`, `revoke`, `remote-revoke`, `rotate-key`, `reencrypt`, and `validate-config` commands; it accepts only secret file paths (never literals) and delegates DDL to the explicit primitives.

Dependency direction inside the module: `authorization_service` → `authorization_transaction_store` → `delegated_custody` → `custody_crypto`; `delegated_invoke` and `authorization_service` share `decode_delegated_human_claims` but do not depend on each other. The gateway orchestrator depends on all of them only through optional injection points (`challenge_producer`, `delegated_requester`) so the live target remains disabled.
