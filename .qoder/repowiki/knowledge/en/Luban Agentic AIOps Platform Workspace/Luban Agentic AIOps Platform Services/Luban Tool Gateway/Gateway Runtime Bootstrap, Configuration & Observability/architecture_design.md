Two-layer runtime composition under `tool_gateway/core`:

- Process bootstrap (`main.py`) is a thin `run()` that loads `GatewayRunSettings` (host/port) and calls `uvicorn.run(app)`.
- Application assembly lives in `app.py::create_app()`, which is the single composition root: it builds a `ToolRegistry` gated by feature flags (`k8s_enabled`, `elastic_enabled`, `skills_service_url`, `incidents_service_url`, `browser_enabled`, `http_enabled`, `secrets_enabled`, `ansible_mcp_enabled` / `ansible_native_enabled`, `servicenow_enabled`), attaches optional cross-cutting services on `app.state` (`tool_registry`, `browser_connector`, `secret_delivery_buffer`, `authorization_service`), registers an HTTP middleware for request-id correlation and structured audit logging, includes the API router, then wires Prometheus metrics and OTel telemetry.
- `core/config.py` defines two frozen dataclasses: `GatewayRunSettings` (process-level host/port) and the large `GatewaySettings` (feature toggles, connector wiring, SPEC-070 delegated execution/acquisition/authorization trust sets). `from_env()` maps `GATEWAY_*` env vars; `__post_init__` enforces fail-closed validation per feature gate (password policy tightening, transport allowlist, Postgres custody + keyring + trusted callback, separate human/workload JWKS issuers/audiences/allowlists). A module-level `@lru_cache(maxsize=1) get_settings()` provides singleton access.
- Cross-cutting concerns are isolated: `metrics.py` (prometheus_client RED surface plus `/metrics` endpoint, mirrored to OTel via `MetricsMirror`), `telemetry.py` (opt-in OTLP push pipeline with lazy imports, fail-open setup, log bridge, HTTPX instrumentation), `observability.py` (root logger configuration and `log_event` JSON-line emitter), `request_context.py` (bounded `x-request-id` resolution bridging to OTel trace id, `execution_id` audit metadata, user-id fallback chain), and `dependencies.py` (FastAPI dependency returning `ToolRegistry` from `request.app.state`).
- Dependency direction is one-way outward: this package depends on `tool_gateway.tools.*` connectors and `tool_gateway.metadata`, but nothing inside `core` is imported by them — they only consume the registry and settings exposed at runtime.
