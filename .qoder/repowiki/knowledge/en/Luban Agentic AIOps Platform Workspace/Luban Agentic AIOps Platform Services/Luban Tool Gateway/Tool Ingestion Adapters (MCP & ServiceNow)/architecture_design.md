Two parallel ingestion strategies share the same SPEC-007 `BaseTool`/`ToolDefinition`/`ToolRegistry` seam so callers see an identical signed-tool surface regardless of transport.

- Generic MCP path: `mcp_adapter.py` defines `McpIngestionConnector` + `McpTool`, which wrap the official `mcp` Python SDK, validate parameters against a gateway-owned JSON-Schema subset, project arguments via `AdmittedTool.argument_map`, and map server responses to `ToolResult`. Transport selection (`streamable_http` vs `stdio`) is driven by `McpTransport`; the SDK is imported lazily so a missing install fails closed with `MCP_SDK_UNAVAILABLE` rather than at import time. Authentication goes through `resolve_outbound_auth` plus an injected `OAuth2TokenClient`, with a separate `AcquisitionContext` seam for SPEC-070 user-delegated OAuth flows.
- Per-target bindings: `ansible_binding.py` supplies the admitted allowlist, canonical names, schemas, and tiers consumed by the generic adapter; `servicenow_native.py` takes a different route because ServiceNow's MCP server is unavailable on the operator PDI, instead implementing a direct `httpx` Table-API client with fixed table names, regex-validated `sys_id`, field projection, and bounded pagination.
- The module exposes no runtime registry itself — consumers construct a connector and call `register_tools(registry)`.
- Dependency direction is one-way: bindings depend on the generic adapter; neither adapter depends on the other. Both depend only on `tool_gateway.tools.*` primitives and never touch the kernel directly.
