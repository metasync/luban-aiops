This leaf is a pure contract layer with no executable code. It publishes two kinds of artifacts:
- JSON Schema files (`execution-request.schema.json`, `execution-receipt.schema.json`, `execution-handoff-response.schema.json`, `execution-observation.schema.json`, `execution-recovery.schema.json`, `tool-result.schema.json`) using draft-2020-12, each with a canonical `$id` under `metasync.github.io/luban-aiops/schemas/`. The request schema uses a `oneOf` discriminator to support both legacy v2 envelopes (no `protocol_version`/`expires_at`/`run_id`/`admission_epoch`) and the current v3 envelope carrying requester/decider identity, `approval_kind`, and HMAC-SHA256 signatures over canonical JSON.
- SQL migration files (`execution-ledger-v1.sql`, `execution-ledger-v2.sql`) defining the PostgreSQL execution ledger: `execution_protocol_state` (singleton schema-version/admission flag), `execution_runs`, `execution_intents` (request envelopes stored as jsonb with exhaustive CHECK constraints mirroring the JSON schemas — field presence, type, length, digest regexes, enum values), `execution_dispatch_claims` (per-attempt ownership), `execution_observation_state`, and `execution_observations` (ordered append-only observation log).

Dependency direction is one-way: the SQL layer enforces the same invariants declared in the JSON schemas via inline `CHECK` clauses (e.g. `request_envelope ?& ARRAY[...]`, `execution_json_strings`, digest regexes, `approval_kind IN ('action','flow')`), so the schemas are the human-readable contract while the DB is the authoritative enforcement point. There is no runtime code here; consumers in the agent-service build and verify these envelopes against the schemas and persist them through the migrations.
