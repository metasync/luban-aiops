Three cooperating layers form the SPEC-063 / SPEC-070 invocation boundary:

- `execution_invocation.py` is the synchronous coordinator (`coordinate_v3_invocation`). It enforces R-4 ordering: stop check → register intent → dispatch via `handoff_original` → durably accept → mint single-use secret-release permit. It classifies failures into `_PRE_DISPATCH` (provable no-effect) vs `_UNCERTAIN` (possible send) and emits agent observations only when they can be attributed.
- `execution_recovery.py` owns the PostgreSQL-backed evidence ledger (`ExecutionRecovery`). It uses `psycopg` with advisory locks (`pg_try_advisory_lock`) per run_id to serialize concurrent writes, `REPEATABLE READ` snapshots for reads, and an append-only `execution_observations` table with reserved slots (`wait_expired`, `run_stopped`, `response_accepted`). State machines are closed tuples (`RECOVERY_STATES`, `TOOL_REPORT_STATUSES`, `RECOVERY_AVAILABILITY`). Owner-scoped paging uses HMAC-bound cursors (`_encode_cursor`/`_decode_cursor`) keyed by session + owner + scope so cursor tokens cannot be replayed across owners.
- `execution_worker_client.py` is the blocking HTTP client against the execution-runtime worker at `/api/v1/executions/handoff`. `handoff()` is the legacy path; `handoff_original()` is the v3 path that validates the request envelope, enforces all-or-none identity quartet (`requester_namespace`, `requester_sub`, `decider_namespace`, `decider_sub`), carries the requester bearer separately from the approver's `delegated_token`, and returns only a `VerifiedOriginal` — never raw tool output.

Dependency direction is one-way: invocation → worker client → recovery (for registration/accept). The recovery module depends on `execution_protocol` and `execution_signing` but not on the worker client, keeping the ledger writer independent of transport. Runtime dependency injection (`connection_factory=connect`, `get_runtime_kernel()._execution_recovery()`) lets admission be disabled without changing call sites.
