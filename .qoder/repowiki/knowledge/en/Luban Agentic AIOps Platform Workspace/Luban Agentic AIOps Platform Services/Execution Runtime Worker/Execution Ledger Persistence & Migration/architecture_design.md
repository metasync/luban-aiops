Two-layer design split between runtime persistence and deployment-time migration.

- `execution_ledger.py` defines the in-process API: `ExecutionLedger` owns DSN/key/epoch, exposes `claim`, `open_send`/`finish` (permit-burn + advisory-lock linearization), `append`, `stop`, `lookup`, `retention_sweep`, plus read-only `health`/`metrics_snapshot`. A private `DispatchPermit` is minted only after a committed claim row and cannot be serialized or copied; it gates the final send path. All writes go through `psycopg` with explicit `conn.transaction()` blocks; reads use `SET TRANSACTION READ ONLY` / `REPEATABLE READ`.
- `execution_migration.py` is an operator CLI (`migrate`, `verify_schema`, `fingerprint`) that loads SQL from package resources under `contracts/`, applies v1 then v2 via a fenced `pg_advisory_xact_lock(-630001)` transaction, and records a `schema_fingerprint` digest of tables/constraints/triggers/indexes/functions so every runtime call re-validates the deployed schema before proceeding.
- `contracts/` holds the authoritative DDL: `execution-ledger-v1.sql` creates `execution_protocol_state`, `execution_runs`, `execution_intents`, `execution_dispatch_claims`, `execution_observations`, `execution_observation_state` plus immutability and monotonicity triggers; `execution-ledger-v2.sql` drops the old closed-envelope constraint and adds `requester_namespace/sub` / `decider_namespace/sub` fields required by SPEC-070's attribution model.
- Dependency direction is one-way: ledger depends on migration (`connect`, `verify_schema`) and on shared protocol/signing helpers; contracts are pure SQL assets consumed at deploy time.
- Safety boundaries: no leases/takeover, no memory fallback, no live target enabling — admission starts disabled and is gated by epoch checks against `execution_protocol_state`; retention sweep is bounded per-call and protected by a `luban.execution_retention` session setting checked by the `execution_immutable` trigger.
