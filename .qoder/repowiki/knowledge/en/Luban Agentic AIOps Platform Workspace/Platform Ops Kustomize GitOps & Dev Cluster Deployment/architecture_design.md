The module is organized around four concerns under `shared/platform-ops/`:
- `gitops/dev-k8s/base/` — the canonical Kustomize base declaring every platform service (agent-platform, audit-service, execution-runtime, identity-broker, incident-service, operator-portal/web-ui, platform-gateway, skills-hub, tool-gateway) plus shared infrastructure (PostgreSQL StatefulSet, Redis, namespace, policy). Each service lives in its own subdirectory with paired `<service>-deployment.yaml` / `<service>-service.yaml` manifests and per-env `runtime-config.env` plus optional `runtime-secrets.env` / `runtime-secrets.example.env` pairs.
- `gitops/runtime-profiles/` — switchable overlays layered on top of base. One LLM provider profile (`default`) is selected at a time via `select-runtime-profile.sh`, while two dev-only postures (`mutating-dev` for bounded mutating tools, `browser-dev` for headless-browser web checks) are always wired in and cannot be selected alone.
- `gitops/*.sh` — operational entry points: `deploy-overlay.sh <overlay-dir>` renders the overlay with `kubectl kustomize --load-restrictor LoadRestrictionsNone` (to pull sample skill docs from `skills/` outside the overlay root), applies it to `dev-luban-aiops`, restarts deployments when `platform-runtime-config` or `platform-policy` ConfigMaps change, and sets image tags sourced from `IMAGE_TAG` or `dev-k8s/.images.env`; `sync-*` scripts provision secrets across namespaces before deployment.
- `e2e/` — shell-based smoke demos exercising each exposed surface (browser-check, documents, incidents, mutating tools, skills).
- `skills/` — source runbooks and alert definitions consumed by the skills-hub via ConfigMap generators in the base overlay.
Dependency direction is one-way: overlays depend on shared infra and skills; scripts depend only on `kubectl`/`kustomize` CLI; no application business logic lives here.
