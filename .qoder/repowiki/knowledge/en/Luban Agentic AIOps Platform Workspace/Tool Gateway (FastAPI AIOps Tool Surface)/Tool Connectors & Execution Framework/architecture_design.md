The module is organized around a small core plus pluggable connector modules:
- `base.py` declares the `BaseTool` ABC, the immutable `ToolDefinition` metadata (name, description, risk_level, category, parameters_schema), the `ToolResult` envelope with an `evidence` sub-object, and factory helpers (`build_evidence`, `make_error_result`, `make_denied_result`).
- `registry.py` implements `ToolRegistry`, which validates `risk_level` against `VALID_RISK_LEVELS` (`read` | `write` | `admin`) and refuses mutating tools unless `allow_mutating=True` (the mechanical backstop for `GATEWAY_MUTATING_TOOLS_ENABLED`). It provides `register`, `get`, `list_definitions`, and `invoke` — the latter always returning a structured `ToolResult` even on unknown-tool or exception paths.
- Each connector file (e.g. `elastic_connector.py`, `k8s_connector.py`, `incidents_connector.py`, `browser_connector.py`, `skills_connector.py`) defines one connector class that owns client lifecycle and exposes a `register_tools(registry)` method registering one or more `BaseTool` subclasses. Tools are grouped by domain and named with a `<domain>.<action>` scheme.
- The browser connector is the most complex: it delegates session management to `browser_sessions.py` (`BrowserSessionPool`, `BrowserSessionEntry`, `FlowState`), credential resolution to `credential_sets.py` (`CredentialSetStore`), and output sanitization to `redaction.py`. It wraps every web tool in `_SessionSerializedTool` so per-chat-session interactions are serialized through an `interaction_lock`, and enforces origin allowlisting, flow binding/deviation guards, and secret masking at multiple points.
- Dependency direction is strictly inward: connectors depend only on `base` and `registry`; `browser_connector.py` additionally depends on the sibling `browser_sessions`, `credential_sets`, and `redaction` modules. There are no cross-connector dependencies.
