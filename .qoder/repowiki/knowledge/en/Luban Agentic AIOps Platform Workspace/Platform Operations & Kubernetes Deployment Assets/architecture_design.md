The module is organized around three concerns:
- `gitops/dev-k8s/` — a Kustomize overlay rooted at `base/kustomization.yaml` that declares the full platform stack (agent-platform, audit-service, execution-runtime, identity-broker, incident-service, operator-portal/web-ui, platform-gateway, skills-hub, tool-gateway) plus shared infrastructure (PostgreSQL StatefulSet, Redis, namespace, policy). Each service lives in its own subdirectory with paired deployment/service manifests and per-service `runtime-config.env` / `runtime-secrets.env` files. A top-level `platform-runtime-config` ConfigMap is assembled by merging all service env files via `configMapGenerator`, and a `platform-policy` ConfigMap holds cluster-wide policy.
- `gitops/runtime-profiles/` — switchable overlays layered on top of base: one LLM provider profile (`default`) selected at a time via `select-runtime-profile.sh`, plus two always-wired dev postures (`mutating-dev` for bounded mutating tools, `browser-dev` for headless-browser web checks) that are never switchable.
- `gitops/*.sh` — operational scripts that drive deployment (`deploy-overlay.sh` uses `kubectl kustomize --load-restrictor LoadRestrictionsNone` to pull sample skill docs from `shared/platform-ops/skills/`), select active runtime profiles, and sync secrets across namespaces (`sync-*` scripts for audit, browser credentials, delegation, execution handoff/signing, incidents, OTel, sessions DB, skills, runtime config).
- `e2e/` — shell-based smoke demos exercising each exposed surface (browser-check, documents, incidents, mutating tools, skills).
- `skills/` — source runbooks and alert definitions consumed by the skills-hub via ConfigMap generators in the base overlay.
The entry point is `deploy-overlay.sh <overlay-dir>` which applies the overlay, restarts deployments when ConfigMaps change, and sets image tags pulled from `.images.env` or `IMAGE_TAG`. Dependency direction is one-way: overlays depend on shared infra and skills; scripts depend only on `kubectl`/`kustomize` CLI.
