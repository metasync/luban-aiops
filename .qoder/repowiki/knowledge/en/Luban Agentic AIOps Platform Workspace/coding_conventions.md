- Each product follows a uniform layout of `src/<service_name>/` split into `api/`, `core/`, `schemas/`, `services/`, optional `tools/` or `policies/`, plus a sibling `tests/` directory, with `app.py`, `main.py`, and `metadata.py` as entry points.
- Inter-service boundaries are enforced exclusively through JSON Schema files in `shared/shared-contracts/schemas/`; products validate requests/responses against these schemas rather than importing shared types.
- Feature work is governed by Spec-Driven Development: new capabilities require a `docs/specs/SPEC-NNN-<slug>/` triad (spec.md requirements, plan.md technical approach, tasks.md execution checklist) with status transitions draft → approved → in-progress → delivered, and acceptance criteria must map to at least one asserting test.
- Cross-cutting configuration and behavior are exposed via environment variables validated in each product's `core/config.py`, with defaults documented in the product README and surfaced through the gateway's runtime settings surface.
- Policy evaluation uses a deny-by-default bundle in `shared/shared-contracts/policies/policy-default.yaml` copied to each consumer via `make sync-policy`, with outcomes `allow`, `deny`, `require_approval` evaluated by precedence and priority across both gateway engines.
- Observability conventions (metrics naming, OTel switches, `x-request-id` ↔ `trace_id` bridging) are defined once in `shared/shared-contracts/observability-conventions.md` and implemented uniformly across all Python services.
