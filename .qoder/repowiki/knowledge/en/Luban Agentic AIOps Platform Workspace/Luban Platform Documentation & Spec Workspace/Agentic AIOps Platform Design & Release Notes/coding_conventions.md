- Release notes are named `<YYYY-MM-DD>-<short-title>.md` and each entry ties an implementation wave to a SPEC number and a versioned release (e.g. `SPEC-054 (v0.35.0)`), with `release-notes/README.md` maintaining the canonical index.
- Each release note follows a dense prose template that enumerates delivered requirements (R-1, R-2, …), lists every new route/action/schema/audit event/migration introduced, and closes with a 'no contract/policy/audit change' or equivalent impact statement.
- The top-level document set is organized as a fixed sequential reading path (decision matrix → reference architecture → identity/authorization → authorization matrix → policy specification → runtime options → delivery roadmap → release notes) rather than ad-hoc navigation.
- Design artifacts are split by concern: framework/architecture in `part-1*` / `part-2*`, identity/authorization in dedicated files, machine-enforceable policy in `policy-specification.md`, and operational sequencing in `delivery-roadmap.md`, keeping concerns decoupled.
