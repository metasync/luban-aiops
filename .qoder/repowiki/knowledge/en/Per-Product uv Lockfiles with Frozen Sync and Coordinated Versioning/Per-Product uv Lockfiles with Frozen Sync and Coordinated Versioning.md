# Dependency Management in the Luban AIOps Platform

## System Overview

The repository uses **uv** as the sole Python dependency manager across all eight backend products (`agent-platform`, `audit-service`, `execution-runtime`, `identity-broker`, `incident-service`, `platform-gateway`, `skills-hub`, `tool-gateway`). Each product is a standalone [PEP 621](https://peps.python.org/pep-0621/) package declared in its own `pyproject.toml` under `products/<name>/`, paired with a committed `uv.lock` lockfile. There are no monorepo-level `pyproject.toml`, no `requirements.txt`, and no vendored third-party source — every dependency is resolved from PyPI (source registry `https://pypi.org/simple`) at build time.

## Key Files

- Per-product manifests: `products/*/pyproject.toml` — declare runtime dependencies, `dependency-groups.dev`, entry-point scripts, and `requires-python = ">=3.11"`.
- Per-product lockfiles: `products/*/uv.lock` — fully pinned transitive graph with SHA256 hashes for wheels/sdists; generated by `uv lock`.
- Shared Make fragments: `mk/python.mk` — defines the canonical `sync` target that runs `uv sync --frozen` per product.
- Root orchestrator: `Makefile` — lists `PYTHON_PRODUCTS`, dispatches `make -C products/$p sync|test|build|push`, and enforces version lockstep via `validate-version`.
- Base image: `shared/base-images/base-uv/Dockerfile` — pins a specific `uv` version and Python interpreter; product Dockerfiles build on top of it.
- Product `.python-version` files — pin the exact CPython minor/major used by each product's `uv sync` resolution.
- Documentation enforcing the pattern: `docs/workspace/backend-service-layout-convention.md` and `docs/workspace/python-container-strategy.md` both mandate `uv.lock` + `uv sync --frozen --no-dev` in container builds.
- Release note documenting policy: `docs/agentic-aiops-platform/release-notes/2026-08-28-dependency-hygiene.md` codifies the "latest stable only" adoption posture and OTel instrumentation exception.

## Architecture and Conventions

### Per-product isolation
Each service owns its own dependency surface. Dependencies are not shared through a workspace-level manifest; instead, common libraries (FastAPI, Pydantic, httpx, cryptography, PyJWT, PyYAML, Prometheus client, OpenTelemetry SDK/exporters/instrumentation) are re-declared with identical version ranges across products so they resolve to the same versions when locked.

### Version range strategy
Runtime dependencies use **upper-bound caps** (e.g. `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`, `cryptography>=43.0,<51.0`, `redis>=6.2,<7.0`, `elasticsearch>=8.0,<9.0`, `kubernetes>=30.0,<33.0`, `playwright>=1.48,<2.0`, `agentscope>=2.0.4,<3.0`, `agentscope-runtime>=1.1,<2.0`). This allows patch/minor updates within a major while preventing breaking upgrades. Dev-only tooling lives in `[dependency-groups] dev` (pytest, jsonschema, fakeredis) and is excluded from production images.

### Deterministic builds
- `uv sync --frozen` is the only supported install command in CI and local workflows (see `mk/python.mk` and `CONTRIBUTING.md`). The `--frozen` flag forces installation strictly from `uv.lock`; any drift fails the build.
- Container images run `uv sync --frozen --no-dev` during build, copying only sources into the prebuilt `luban-aiops/base-uv` image.
- `uv.lock` records `revision = 3` and `requires-python = ">=3.11"`, plus platform markers for Windows vs Linux and Python 3.12/3.13/3.14, ensuring cross-platform determinism.

### Coordinated versioning
All products share a single semantic version (`0.33.0` in their `pyproject.toml`), synchronized against the root `VERSION` file. The root `Makefile` target `validate-version` invokes `shared/shared-contracts/scripts/validate_version.py` to enforce this lockstep. Image tags are computed once from `PLATFORM_VERSION` and reused across all services via `.images.env`.

### Private registries / vendor strategy
No private PyPI registry or vendoring is configured. All packages resolve from `https://pypi.org/simple` as recorded in the lockfiles. If a private registry is needed, it would be supplied via uv configuration outside the repo (the base image carries uv but no project-scoped config).

### Build system integration
- `make sync` iterates `PYTHON_PRODUCTS` and runs `make -C products/$p sync` → `uv sync --frozen`.
- `make test` does the same then runs pytest under disabled OTLP exporters to avoid noise.
- `make build` calls per-product `make build IMAGE_TAG=...` which layers on the shared `base-uv` image.
- `make verify` is the pre-commit/pre-push gate: runs tests, kustomize overlay checks, policy validation, and version lockstep validation.

## Conventions and Constraints

- **Adopt latest stable only**: documented in the dependency hygiene release note; alpha/beta/RC/dev builds are rejected except for the OpenTelemetry instrumentation packages, which live on upstream's permanent `0.xb` channel and stay paired with their locked SDK version.
- **Upper-bound major caps** on all runtime dependencies to prevent silent breaking upgrades.
- **Frozen installs everywhere**: `uv sync --frozen` is required in CI, local development, and container builds; non-frozen installs are not part of the verified workflow.
- **Dev vs prod separation**: dev-only packages are isolated in `[dependency-groups] dev` and excluded from images via `--no-dev`.
- **Single Python version**: `requires-python = ">=3.11"` plus per-product `.python-version` pins ensure deterministic interpreter selection.
- **Shared base image**: all containers derive from `luban-aiops/base-uv:al2023`, built by `make base-images`, carrying a pinned uv and non-root `app` user.
- **Version lockstep**: product `version` fields must match the root `VERSION` file, enforced by `make validate-version`.
- **Policy-driven new products**: new services must follow the layout convention (`Makefile`, Dockerfile on `base-uv`, `pyproject` + `uv.lock`, `.python-version`, src tree mirroring existing products) as specified in multiple SPEC task lists.
