## Approach

The Luban workspace is a Python monorepo whose dependency management is built around **uv** as the package manager, with one `pyproject.toml` + `uv.lock` pair per product under `products/<name>/`. There is no shared Python workspace manifest — each product declares its own runtime and dev dependencies. The Node-based operator portal (`products/operator-portal/web-ui/app/package.json`) uses npm-style `package.json` with caret ranges; it has no lockfile committed.

## Key Files

- `mk/python.mk` — shared Make targets that invoke `uv sync --frozen` and `uv run pytest`, enforcing locked installs for every Python product.
- `mk/defaults.mk` — pins the base image's `BASE_UV_UV_VERSION = 0.12.1` and `BASE_UV_PYTHON_VERSION = 3.12`; these are the single source of truth for reproducible container builds.
- `products/*/pyproject.toml` — per-product dependency declarations (e.g. `agent-service` depends on `agentscope>=2.0.4,<3.0`, `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`, `redis>=6.2,<7.0`, `psycopg[binary]>=3.2,<4.0`).
- `products/*/uv.lock` — fully resolved, hashed lockfiles generated by uv (version 1, revision 3), pinning transitive dependencies to exact versions from `https://pypi.org/simple`.
- `products/*/Dockerfile` — build images using the shared `shared/base-images/base-uv` image whose uv/python versions come from `mk/defaults.mk`.
- `.python-version` at repo root and per-product `.python-version` files — declare the preferred interpreter (3.12).
- `Makefile` — top-level `sync` target iterates `PYTHON_PRODUCTS` and delegates to each product's `make sync`.

## Architecture and Conventions

1. **Frozen resolution**: Every install goes through `uv sync --frozen` (see `mk/python.mk`). This rejects any change in `uv.lock` or `pyproject.toml` that would alter the resolved tree, so CI and local runs produce identical environments.
2. **Per-product isolation**: No cross-product Python dependencies are declared. Products communicate via HTTP/gRPC contracts in `shared/shared-contracts/`, not via shared packages.
3. **Base image strategy**: `make base-images` builds `luban-aiops/base-uv:<al2023>` from `shared/base-images/base-uv/Dockerfile` with pinned `UV_VERSION=0.12.1` and `PYTHON_VERSION=3.12`; all product images layer on top of this image, ensuring the same uv binary across the fleet.
4. **Version pinning style**: Runtime dependencies use upper-bound major-version constraints (e.g. `>=X.Y,<Z.0`) rather than exact pins in `pyproject.toml`; exact pins live only in `uv.lock`. Dev dependencies follow the same pattern.
5. **No private registry**: All `source = { registry = "https://pypi.org/simple" }` entries in the lockfiles point to public PyPI. No `PYPI_URL`, `UV_INDEX_URL`, `pip.conf`, or `GOPRIVATE` configuration was found anywhere in the repository.
6. **Node dependencies**: The operator portal's SPA uses `package.json` with caret ranges (`^`) and no committed lockfile; the `make verify` gate does not include an npm lockstep step for it.
7. **Build system declaration**: Each Python product sets `[build-system].requires = ["uv_build>=0.8.14,<0.9.0"]` and `build-backend = "uv_build"`.

## Conventions and Constraints

- **Rule**: Dependency installation must go through `make sync` (root) or `make -C products/<name> sync`, which runs `uv sync --frozen`. Direct `pip install` or `uv pip install` bypasses the frozen lock and is not part of the documented workflow.
- **Rule**: The base uv version used in container images is pinned to `0.12.1` in `mk/defaults.mk` and propagated via `--build-arg UV_VERSION=$(BASE_UV_UV_VERSION)` when building `shared/base-images/base-uv`.
- **Rule**: The base Python version is pinned to `3.12` in both `mk/defaults.mk` (`BASE_UV_PYTHON_VERSION`) and the per-product `.python-version` files; the agent-platform `pyproject.toml` additionally declares `requires-python = ">=3.11"`.
- **Convention**: Runtime dependencies are declared with semver-compatible ranges (`>=X,<Y`) in `pyproject.toml`; exact resolved versions and hashes are committed in `uv.lock`.
- **Convention**: Dev/test dependencies are grouped under `[dependency-groups].dev` in `pyproject.toml` (e.g. `fakeredis`, `pytest`) and installed alongside runtime deps during development.
- **Constraint**: The root `Makefile` enumerates the Python products explicitly (`PYTHON_PRODUCTS := agent-platform audit-service execution-runtime identity-broker incident-service platform-gateway skills-hub tool-gateway`); adding a new product requires updating this list plus the `IMAGE_PRODUCTS` list to participate in `make sync`, `make test`, and coordinated image builds.
