## System / Approach

The workspace uses **uv** (Astral) as the single Python package and interpreter manager across all backend services. Each product under `products/` is an independent Python package declared in its own `pyproject.toml`, with a co-located `uv.lock` that pins every transitive dependency to exact versions and hashes. The root Makefile enumerates the Python products (`PYTHON_PRODUCTS := agent-platform audit-service execution-runtime identity-broker incident-service platform-gateway skills-hub tool-gateway`) so `make sync` and `make test` iterate over each one, invoking `make -C products/<name> sync` which runs `uv sync --frozen`. There is no monorepo-level lockfile; reproducibility is enforced per-product.

## Key Files

- Per-product manifests: `products/*/pyproject.toml` — declares `[project]` dependencies with semver ranges (e.g. `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`, `opentelemetry-sdk>=1.25,<2.0`), `[dependency-groups].dev` for test-only packages, and a `[build-system]` pinning `uv_build>=0.8.14,<0.9.0` as the build backend.
- Per-product lockfiles: `products/*/uv.lock` — generated by uv, records exact resolved versions, sources (`registry = "https://pypi.org/simple"`), sdist/wheel URLs and SHA256 hashes for every dependency.
- Interpreter pin: `.python-version` at repo root and in each product directory (e.g. `3.12`); consumed by uv during `sync` and by the base image's `UV_PYTHON` fallback.
- Shared build fragments:
  - `mk/python.mk` — shared `sync` / `test` targets that run `uv sync --frozen` then `uv run pytest` with OTLP exporters disabled.
  - `mk/image.mk` — shared Docker build/push/lint targets used by every product `Makefile`.
  - `shared/base-images/base-uv/Dockerfile` — builds the `luban-aiops/base-uv:al2023` image on Amazon Linux 2023 minimal with a pinned `uv` version (`UV_VERSION=0.12.1`) installed from `https://astral.sh/uv/${UV_VERSION}/install.sh`; sets `UV_LINK_MODE=copy`, `UV_NO_SYNC=1`, `UV_PYTHON=<ARG>`, `UV_PYTHON_INSTALL_DIR=/app/.python`, and creates a non-root `app` user (uid 1000).
- Product Dockerfiles (e.g. `products/agent-platform/Dockerfile`) follow the documented pattern: `FROM luban-aiops/base-uv:al2023`, copy `.python-version pyproject.toml uv.lock README.md ./src`, then `RUN uv sync --frozen --no-dev`, and `CMD ["uv", "run", "<service-script>"]`.
- Root orchestration: `Makefile` — aggregates per-product `sync`/`test`, builds images with a coordinated `IMAGE_TAG`, and drives verification gates.
- Strategy doc: `docs/workspace/python-container-strategy.md` — documents the adopted Option B base-image strategy and the rules around it.

## Architecture and Conventions

- **Per-package isolation**: Each service owns its own `pyproject.toml` and `uv.lock`; there are no cross-package Python imports between services, so dependency drift is contained.
- **Semver range policy**: Dependencies use bounded upper limits (e.g. `<1.0`, `<2.0`, `<3.0`, `<7.0`) to prevent breaking upgrades while allowing patch/minor updates. Dev-only tools live in `[dependency-groups].dev`.
- **Frozen installs everywhere**: Both development (`mk/python.mk`) and production (`Dockerfile RUN uv sync --frozen --no-dev`) use `--frozen`, meaning the lockfile is the source of truth — no resolution against the network is allowed at install time.
- **Shared base image**: All Python services build from the centrally built `luban-aiops/base-uv:al2023` image (built via `make base-images`). The base image pins `uv` and `PYTHON_VERSION` via ARGs and exports deterministic environment variables (`PYTHONDONTWRITEBYTECODE`, `PYTHONUNBUFFERED`, `UV_LINK_MODE=copy`, `UV_NO_SYNC=1`, `UV_PYTHON`, `UV_PYTHON_INSTALL_DIR`).
- **Non-root runtime**: The base image creates uid 1000 `app` user; deployment security contexts enforce `runAsNonRoot`, `allowPrivilegeEscalation: false`, `seccompProfile: RuntimeDefault`.
- **No vendoring**: No `vendor/` directories or checked-in wheels; all third-party code comes from PyPI via uv's resolver and lockfile.
- **No private registry configured in code**: The lockfiles reference `source = { registry = "https://pypi.org/simple" }`; any private registry would need to be supplied via uv configuration outside this repo.

## Conventions and Constraints

- **Interpreter selection**: Every product must have a `.python-version` file; the shared base image's `UV_PYTHON` defaults to the ARG value, but `uv sync` resolves the interpreter from `.python-version` first.
- **Lockfile immutability in CI/build**: `uv sync --frozen` is used in both `make test` and Docker `RUN` steps; any drift requires regenerating the lockfile before committing.
- **Build backend pin**: All products declare `[build-system] requires = ["uv_build>=0.8.14,<0.9.0"]` and `build-backend = "uv_build"`, ensuring reproducible sdist/wheel builds.
- **Base image lifecycle**: The base image is rebuilt via `make base-images` (a prerequisite of `make build`); `BASE_UV_UV_VERSION` and `BASE_UV_PYTHON_VERSION` defaults in `mk/defaults.mk` must be bumped together with any workspace-wide toolchain migration, never defaulting to `latest`.
- **Image tag coordination**: The root `Makefile` computes a single `IMAGE_TAG` and writes it into `shared/platform-ops/gitops/dev-k8s/.images.env`, so all product images share one coordinated tag per build.
- **Verification gate**: `make verify` runs `test`, `overlays`, `validate-policy`, `validate-policy-scenarios`, `validate-version`, and `validate-secret-vocabulary`; failing any step blocks merges in CI.
- **Container strategy rule** (from `docs/workspace/python-container-strategy.md`): all Python backend images must build `FROM luban-aiops/base-uv:al2023`, keep `.python-version` and `uv.lock` in the image, use `uv sync --frozen --no-dev`, set `UV_NO_SYNC=1`, and run as the non-root `app` user.
