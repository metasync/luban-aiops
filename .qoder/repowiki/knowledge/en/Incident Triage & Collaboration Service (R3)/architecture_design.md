Single FastAPI product under `products/incident-service` following the repo's shared service layout: `api/routes` exposes `/api/v1/webhooks/alertmanager`, `/api/v1/incidents*`, and health; `services/` holds domain logic (`normalization` for Alertmanager v4 payloads, `triage` orchestrating one agent turn against agent-platform `/api/v2/chat`, `connectors` registry, `incident_store` protocol with in-memory and Postgres backends, `query_auth` for Basic/workload-token callers); `core/` provides frozen `IncidentSettings`, metrics, observability, request-context, and telemetry. The app lifecycle (`app.py`) builds connectors and store at startup and fails fast on unknown connector names. Triage uses a dedicated per-incident session (`incident-<id>`) with a per-operator fallback to handle single-owner sessions, prefers kernel-validated `structured_output` over a fenced `` ```triage-report ``` `` block, and always forces server-minted attribution fields (`session_id`, `generated_at`, `generated_by`). The connector framework (`services/connectors.py`) defines a `Connector` Protocol plus an `audit` built-in sink; dispatch failures are recorded but never bubble up, keeping triage success independent of collaboration outages. Tool-gateway adds read-only `incidents.list` / `incidents.get` tools via `tools/incidents_connector.py`, authenticating with gateway-held credentials and mapping upstream errors to structured tool results.
