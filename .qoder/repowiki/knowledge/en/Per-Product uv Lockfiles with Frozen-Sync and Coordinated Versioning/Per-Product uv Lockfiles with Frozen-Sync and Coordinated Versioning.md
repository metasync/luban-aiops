## System Overview

The Luban platform uses a **per-product dependency management** model built on `uv` (Python) and `npm`/`vite` (portal), coordinated by a root Makefile that orchestrates sync, build, test, and verification across all eight Python products plus the operator portal. There is no monorepo-level lockfile; each product owns its own `pyproject.toml` + `uv.lock` pair, and the frontend lives in `products/operator-portal/web-ui/` with its own `package.json` / `package-lock.json`.

## Key Files and Packages

- Per-product manifests: `products/*/pyproject.toml` declare runtime dependencies, dev dependency groups (`[dependency-groups] dev = [...]`), entry-point scripts (`[project.scripts]`), and the `uv_build` backend (`requires-python = ">=3.11"`, pinned `uv_build>=0.8.14,<0.9.0`).
- Per-product lockfiles: `products/*/uv.lock` — generated by `uv lock`; consumed via `uv sync --frozen` so CI and local runs resolve to an exact snapshot.
- Shared build fragments: `mk/python.mk` defines the canonical `sync` (`uv sync --frozen`) and `test` targets included by every Python product's `Makefile`.
- Root orchestration: `Makefile` lists `PYTHON_PRODUCTS := agent-platform audit-service execution-runtime identity-broker incident-service platform-gateway skills-hub tool-gateway` and dispatches `make -C products/$p sync|test|build|push`.
- Frontend: `products/operator-portal/web-ui/package.json` (Node ≥22.22.2 per SPEC-042), `package-lock.json`, Dockerfile building with `tsc --noEmit && vite build`.
- Shared SDK placeholder: `shared/shared-sdk/README.md` reserves a module for future shared service clients/auth/tracing helpers but currently contains no code.
- Policy contracts: `shared/shared-contracts/policies/` holds canonical policy bundles copied into consumers via `make sync-policy`.

## Architecture and Conventions

### Frozen lockfiles as the source of truth
Every Python product installs from its locked snapshot using `uv sync --frozen`. The root `make verify` target chains tests, overlay rendering, policy validation, version validation, secret-vocabulary validation, password-policy validation, and a local secret-delivery demo — ensuring the lockfile stays consistent with behavior.

### Latest-stable-only adoption policy
SPEC-042 codifies a repository-wide rule: adopted versions must be final stable releases — no alpha, beta, RC, or dev builds. The only recorded exception is the OpenTelemetry instrumentation packages (`opentelemetry-instrumentation-fastapi`, `-httpx`, `-logging`), which ship on a permanent `0.xb` channel and stay paired with their locked SDK version. This policy is enforced by the spec's acceptance criteria and by the release-note discipline that records every adopt decision.

### Range-based declarations with explicit cap adjudication
Dependencies are declared as semver ranges in `pyproject.toml` (e.g. `fastapi>=0.115,<1.0`, `cryptography>=43.0,<51.0`, `redis>=6.2,<7.0`, `elasticsearch>=8.0,<9.0`). When a range cap is intentionally held back (Redis client `<7.0`, Elasticsearch client `<9.0`), the reason is documented in the spec/release notes rather than silently frozen. Major bumps require a call-site review (e.g. cryptography 43→51 reviewed JWT/signing surfaces).

### Coordinated versioning across products
All Python products pin the same package version string in their `pyproject.toml` (`version = "0.41.1"` in agent-platform, tool-gateway, platform-gateway). A root script `shared/shared-contracts/scripts/validate_version.py` enforces lockstep between the root `VERSION` file, every product's `metadata.py`, and the portal. The root `Makefile` exposes `make validate-version` as part of `make verify`.

### Container image base pinning
A shared base image `shared/base-images/base-uv/Dockerfile` is built once with `BASE_UV_UV_VERSION` and `BASE_UV_PYTHON_VERSION` from `mk/defaults.mk`, then referenced by every product Dockerfile. This pins the `uv` binary and Python interpreter used at build time independently of the host environment.

### Portal dependency hygiene
The operator portal follows the same latest-stable-only policy: React 19, antd 6, Vite 8, Vitest 4, TypeScript 5.9, jsdom 30, Node ≥22.22.2. A vitest teardown guard fails the suite when any `[antd: …] … deprecated` warning appears, preventing deprecation drift. The `engines.node` field and the Dockerfile node base image are kept in lockstep with the strictest adopted requirement.

## Conventions and Constraints

- **One lockfile per product**: each `products/<name>/` has its own `pyproject.toml` + `uv.lock`; there is no workspace-level lock.
- **Frozen install everywhere**: `uv sync --frozen` is the only supported install path in CI and local workflows (see `mk/python.mk` and `docs/guides/getting-started.md`).
- **Ranges in manifests, pins in locks**: `pyproject.toml` declares ranges; `uv.lock` carries the resolved versions. Upgrades go through `uv lock` followed by `make verify`.
- **Latest stable only**: no prereleases, betas, RCs, or dev builds may be adopted without a recorded exception (the OTel instrumentation `0.xb` channel is the sole documented exception).
- **Major-version caps are deliberate and documented**: Redis `<7.0` and Elasticsearch `<9.0` are parked with reasons tied to deployed server versions; any change requires spec-level justification.
- **Shared policy bundles are single-source-of-truth**: canonical policies live under `shared/shared-contracts/policies/` and are copied into consumers via `make sync-policy`; consumers do not edit them directly.
- **Version lockstep is enforced**: `make validate-version` checks that the root `VERSION`, product `metadata.py` values, and portal version agree; failure blocks `make verify`.
- **Secret vocabulary lockstep**: `make validate-secret-vocabulary` ensures secret-literal definitions stay synchronized across agent-platform, tool-gateway, and skills-hub.
- **No vendored third-party Python packages**: dependencies are resolved remotely via `uv`'s configured index; no `vendor/` directory exists.
- **Docker images tag with coordinated semver**: `make build` computes a single `IMAGE_TAG` from `VERSION` and writes it into `.images.env`, then tags every product image with that tag, keeping runtime versions aligned.
