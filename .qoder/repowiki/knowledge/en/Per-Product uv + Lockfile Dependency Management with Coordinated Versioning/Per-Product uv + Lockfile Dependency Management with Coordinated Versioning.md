## What system/approach is used

The repository uses **uv** as the Python package manager and resolver for every product. Each service under `products/` declares its runtime and development dependencies in a per-product `pyproject.toml` (PEP 621 format) and pins an exact, reproducible resolution via a per-product `uv.lock` file. The build toolchain is `uv_build` (declared in each product's `[build-system]`). There are no `requirements.txt`, `Pipfile`, `poetry.lock`, or vendored third-party source trees — all dependencies come from PyPI (or whatever registry uv resolves against).

## Key files and packages

- Per-product dependency manifests: `products/*/pyproject.toml` (e.g. `agent-platform`, `platform-gateway`, `audit-service`, `identity-broker`, `incident-service`, `skills-hub`, `tool-gateway`).
- Per-product lockfiles: `products/*/uv.lock` (generated by uv; copied into images alongside `pyproject.toml` and `.python-version`).
- Shared Make targets: `mk/python.mk` defines `sync` (`uv sync --frozen`) and `test` (runs `uv run pytest` after syncing), which every product Makefile includes.
- Root orchestrator: root `Makefile` lists `PYTHON_PRODUCTS := agent-platform audit-service identity-broker incident-service platform-gateway skills-hub tool-gateway` and runs `make -C products/$p sync` / `test` across them.
- Container strategy docs: `docs/workspace/python-container-strategy.md` prescribes copying `.python-version`, `pyproject.toml`, and `uv.lock` into images and running `uv sync --frozen --no-dev` at build time.
- Dockerfiles: every product `Dockerfile` copies exactly those three files before installing dependencies.
- Version coordination script: `shared/shared-contracts/scripts/validate_version.py` enforces that every product's `pyproject.toml [project] version`, runtime metadata (`SERVICE_VERSION` in `src/*/metadata.py`), optional `__version__`, and the operator portal's `PLATFORM_VERSION` match the single root `VERSION` file.

## Architecture and conventions

1. **One product = one dependency graph.** Each service owns its own `pyproject.toml` and `uv.lock`. There is no workspace-level `pyproject.toml` aggregating dependencies; cross-cutting concerns are handled via Make targets and shared scripts instead of a monorepo package manager workspace.

2. **Frozen installs everywhere.** Both developer workflows (`make sync`, `make test`) and image builds use `uv sync --frozen`, guaranteeing that the installed tree matches `uv.lock` exactly. No dependency pinning is done via environment variables or pip flags beyond `--frozen`.

3. **Dev vs runtime separation via dependency groups.** Runtime dependencies live under `[project].dependencies`; test-only tools (`pytest`, `jsonschema`, `fakeredis`) live under `[dependency-groups].dev`. Image builds pass `--no-dev` so dev deps never ship.

4. **Python version pinned per product.** Each product ships a `.python-version` file (e.g. `3.12`); the root also has a `.python-version`. Dockerfiles copy this file so the container uses the same interpreter version as development.

5. **Shared observability stack.** Across services, OpenTelemetry packages (`opentelemetry-sdk`, `opentelemetry-exporter-otlp-proto-http`, `opentelemetry-instrumentation-*`) and `prometheus-client` are declared with aligned upper bounds (e.g. `<2.0`, `<1.0`), keeping telemetry behavior consistent without a shared package.

6. **Coordinated release versioning.** The root `VERSION` file is the single source of truth. `make validate-version` (via `shared/shared-contracts/scripts/validate_version.py`) fails CI if any product's `pyproject.toml` version drifts. This couples dependency updates to coordinated releases because bumping a dependency often requires a version bump.

7. **Policy bundle synchronization.** While not a Python dependency, the policy YAML bundle follows the same pattern: a canonical `shared/shared-contracts/policies/policy-default.yaml` is copied to consumers via `make sync-policy`, mirroring the dependency-lock philosophy.

## Conventions and constraints

- **Every Python product must declare dependencies only in `pyproject.toml`**; no `requirements.txt` or inline `pip install` in Dockerfiles. Enforced by the container strategy documented in `docs/workspace/python-container-strategy.md` and the uniform Dockerfile template.
- **Lockfiles must be committed.** `uv sync --frozen` will fail if `uv.lock` is missing or out of date, making it a hard requirement for deterministic builds.
- **Dependency ranges use caret-style upper bounds** (e.g. `fastapi>=0.115,<1.0`, `pydantic>=2.7,<3.0`, `cryptography>=43.0,<45.0`). Major-version bumps require explicit review since they break the constraint.
- **Build backend is locked to `uv_build>=0.8.14,<0.9.0`** in every product's `[build-system]`, preventing accidental upgrades to incompatible build tooling.
- **CI/verification gate:** `make verify` runs `test overlays validate-policy validate-version`, so any dependency change that breaks tests or drifts versions will fail the pre-commit/pre-push gate defined in the root Makefile.
- **No private registry configuration was found** in the checked files; uv resolves against the default PyPI index unless overridden externally (e.g. via `UV_INDEX_URL`). If a private registry is needed, it would be configured outside these files.
