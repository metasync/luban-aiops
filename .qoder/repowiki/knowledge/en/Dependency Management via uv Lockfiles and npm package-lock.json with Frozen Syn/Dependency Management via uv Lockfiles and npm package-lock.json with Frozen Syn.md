## Approach

Luban is a multi-product Python workspace (nine services under `products/`) plus an operator-portal SPA. Dependency management is split by language:

- **Python**: each product ships its own `pyproject.toml` + committed `uv.lock`. The workspace root has no top-level `pyproject.toml`; there is no PEP 751 workspace, no shared dependency manifest.
- **Frontend**: the operator portal (`products/operator-portal/web-ui/app/package.json`) uses npm with a committed `package-lock.json`.

There is no vendored third-party source tree, no private PyPI registry configured at the repo level, and no `pip.conf` / `PIP_*` environment variables in the build scripts — dependencies resolve from the public index unless overridden externally.

## Key Files

- Per-product manifests: `products/*/pyproject.toml` (8 Python products), `products/operator-portal/web-ui/app/package.json`
- Per-product lockfiles: `products/*/uv.lock`, `products/operator-portal/web-ui/app/package-lock.json`
- Shared build glue: `mk/python.mk` (defines `sync` / `test` using `uv sync --frozen`)
- Root orchestrator: `Makefile` (aggregates per-product `sync`, `test`, `build`, `push`)
- Policy doc: `docs/specs/SPEC-042-dependency-hygiene/spec.md` (the authoritative hygiene policy)
- Base image: `shared/base-images/base-uv/Dockerfile` (pins `UV_VERSION` / `PYTHON_VERSION` used to build all product images)

## Architecture and Conventions

### Python packages

- Every Python product declares itself as a PEP 621 project with `[project]` metadata, `requires-python = ">=3.11"`, explicit `dependencies`, `[dependency-groups].dev` for test-only deps, and `[build-system]` pinning `uv_build>=0.8.14,<0.9.0` as the build backend.
- Runtime ranges are caret-style with major caps (e.g. `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`, `agentscope>=2.0.4,<3.0`). Some ecosystem packages carry deliberate upper bounds: `cryptography>=43.0,<51.0`, `redis>=5.0,<7.0`, `elasticsearch>=8.0,<9.0`, `kubernetes>=30.0,<33.0`.
- Test/dev dependencies live in `[dependency-groups].dev` (e.g. `pytest>=8.3,<9.0`, `fakeredis>=2.26,<3.0`, `jsonschema>=4.23,<5.0`).
- Each product also pins `.python-version` alongside its `pyproject.toml`.

### Frontend package

- `package.json` declares runtime deps (`antd ^6.6.2`, `react ^19.2.8`, `@ant-design/x ^2.9.0`, etc.) and dev deps (`vite ^8.2.2`, `vitest ^4.1.11`, `typescript ~5.9.3`, `jsdom ^30.0.1`).
- `engines.node = ">=22.22.2"` reflects the strictest adopted requirement (jsdom 30).
- `package-lock.json` is committed; the spec requires `package.json` ranges and `package-lock.json` stay consistent.

### Build and install flow

- `make sync` iterates `$(PYTHON_PRODUCTS)` and runs `make -C products/$p sync`, which invokes `uv sync --frozen` (from `mk/python.mk`).
- `make test` first re-runs `uv sync --frozen` then executes `uv run pytest` with OTLP exporters disabled so tracing tests can keep the SDK active without network noise.
- Docker images are built on top of `shared/base-images/base-uv`, whose `UV_VERSION` and `PYTHON_VERSION` are injected via `make base-images` and propagated through `mk/image.mk`.
- The root `Makefile` coordinates image tags across all products into a single `IMAGE_TAG` derived from `VERSION` + git sha + profile.

### Version lockstep

- A single root `VERSION` file is the canonical platform version; every product's `pyproject.toml` `version` field is kept in lockstep (enforced by `make validate-version` running `shared/shared-contracts/scripts/validate_version.py`).
- Release notes consistently record changes to both `__version__` literals and per-product `uv.lock` files together.

### Hygiene policy (SPEC-042)

The delivered SPEC-042 establishes the repository-wide rules:

- **Latest stable only** — no alpha, beta, RC, or dev versions anywhere. One recorded exception: OpenTelemetry instrumentation packages (`opentelemetry-instrumentation-fastapi/httpx/logging`) use their permanent `0.xb` channel because upstream has no stable release line for them.
- Backend lockfiles are refreshed periodically inside declared ranges so each `uv.lock` carries the latest stable version its range allows.
- Range caps on sensitive packages (`cryptography`, `redis`, `elasticsearch`) require an explicit adjudication documented in the spec before being moved.
- antd deprecations in the portal are treated as code migration, not version pinning, with a vitest guard that fails the suite on any `[antd: …] … is deprecated` console warning.
- TypeScript is parked on the 5.x line (5.9.x) for maturity reasons; Node stays on the 22 line.

## Conventions and Constraints

- **Frozen installs in CI and local dev**: `uv sync --frozen` is the only install path exposed by `mk/python.mk`; it rejects any deviation between `pyproject.toml` and `uv.lock`, making lockfiles the single source of truth for resolved versions.
- **No top-level workspace manifest**: each product owns its own `pyproject.toml`; there is no cross-package dependency sharing via a workspace root.
- **Major-version caps on risky transitive/runtime deps**: `cryptography<51.0`, `redis<7.0`, `elasticsearch<9.0`, `kubernetes<33.0` are enforced by the declared ranges in `pyproject.toml` and reviewed explicitly in SPEC-042 rather than left open-ended.
- **Lockfiles must be committed**: release notes repeatedly pair `uv.lock` refreshes with other changes, and `make verify` includes integration tests that run against frozen environments.
- **Portal frontend uses npm + package-lock.json**: `package.json` ranges and `package-lock.json` are required to stay consistent (SPEC-042 R-3); the Docker build runs `tsc --noEmit && vite build`.
- **Node engine floor is pinned**: `engines.node >=22.22.2` in `package.json` matches the jsdom 30 requirement and is reflected in the Dockerfile node base image check.
- **Private registries are not configured in-tree**: no `index-url`, `extra-index-url`, `pip.conf`, `PIP_INDEX_URL`, or `GOFLAGS=-insecure` appears in the build scripts; resolution relies on the default public index unless overridden by the host environment.
