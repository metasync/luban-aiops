## System Overview

The Luban AIOps platform manages dependencies across eight Python microservices and a TypeScript operator portal using a **per-product lockfile strategy** driven by `uv` (the fast Python package manager) for the backend and standard npm tooling for the portal. There is no monorepo-level workspace file; each product under `products/<name>/` declares its own `pyproject.toml`, owns its own `uv.lock`, and pins a `.python-version`. The root `Makefile` orchestrates dependency synchronization, testing, and image builds across all products in one command.

## Key Files and Packages

- **Per-product manifests**: `products/*/pyproject.toml` declare `[project]` dependencies with caret/caret-style ranges (e.g. `fastapi>=0.115,<1.0`, `agentscope>=2.0.4,<3.0`, `pydantic>=2.8,<3.0`) plus optional `[dependency-groups.dev]` test deps (`pytest`, `jsonschema`, `fakeredis`).
- **Per-product lockfiles**: `products/*/uv.lock` — generated by `uv lock`; these are committed to version control and consumed via `uv sync --frozen`.
- **Python version pinning**: `products/.python-version` (root) and per-product `.python-version` files (e.g. `products/agent-platform/.python-version` = `3.12`).
- **Build system**: `mk/python.mk` provides shared `sync` / `test` targets that run `uv sync --frozen` then `uv run pytest`; `mk/image.mk` builds Docker images that `COPY pyproject.toml uv.lock` and install with `uv sync --frozen --no-dev`.
- **Shared base image**: `shared/base-images/base-uv/Dockerfile` built from `mk/defaults.mk` constants `BASE_UV_UV_VERSION=0.12.1` and `BASE_UV_PYTHON_VERSION=3.12`.
- **Version lockstep enforcement**: `shared/shared-contracts/scripts/validate_version.py` reads the single-source `VERSION` file at the repo root and asserts every `products/*/pyproject.toml [project].version`, every `metadata.py` `SERVICE_VERSION`, and any `__init__.py __version__` match it; invoked via `make validate-version`.
- **Policy bundle as a deploy-time dependency**: `shared/platform-ops/gitops/dev-k8s/base/shared/policy.yaml` is copied into gateway services and GitOps overlays via `make sync-policy`.

## Architecture and Conventions

1. **Frozen installs everywhere**. Both development (`make -C products/<name> sync`) and production container builds use `uv sync --frozen`, which refuses to resolve against PyPI and instead uses the committed `uv.lock` exactly. This makes `uv.lock` the authoritative artifact for reproducibility.
2. **Range-declared, lock-resolved dependencies**. `pyproject.toml` declares semver ranges (typically `<major>.0` caps on breaking boundaries like `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`, `cryptography>=43.0,<51.0`). Actual resolved versions live only in `uv.lock`. Upgrades are done by re-running `uv lock` inside the range and committing the new lockfile — never by editing `uv.lock` by hand.
3. **Single source of truth for platform version**. `VERSION` at the repo root is the canonical semver; `make validate-version` enforces that every product's `pyproject.toml` version, service metadata, and portal build-time injection stay in lockstep. The root Makefile also computes a coordinated `IMAGE_TAG` prefix from this value.
4. **Shared base image pins toolchain versions**. `mk/defaults.mk` pins `BASE_UV_UV_VERSION=0.12.1` and `BASE_UV_PYTHON_VERSION=3.12`; the base image `luban-aiops/base-uv:al2023` is built once and reused by every product Dockerfile, ensuring identical `uv` and Python versions across environments.
5. **No vendoring or private registries in-tree**. Dependencies are resolved from the public PyPI index (and npm registry for the portal). No `vendor/` directories, no `pip.conf`/`uv.toml` registry overrides checked in. Private credentials are injected at runtime via Kubernetes secrets synced by scripts under `shared/platform-ops/gitops/` (e.g. `sync-otel-secrets.sh`, `sync-runtime-secret.sh`), not baked into lockfiles.
6. **Dependency hygiene governed by specs**. SPEC-042 (`docs/specs/SPEC-042-dependency-hygiene/spec.md`) codifies the policy: adopt latest stable versions only (no betas/RCs), re-lock every product's `uv.lock` regularly, adjudicate range caps explicitly (e.g. `redis` capped `<7.0` because client majors 7/8 were API-removal releases; `elasticsearch` capped `<9.0` because the client major follows the server major), and record reasons for parked upgrades.
7. **Portal frontend uses conventional npm tooling**. The operator portal (`products/operator-portal/web-ui/`) maintains its own `package.json` + `package-lock.json` (referenced in SPEC-042 R-3/R-4 for antd, vite, vitest, TypeScript, React 19 migration). Its Dockerfile runs `tsc --noEmit && vite build` on a Node base image.

## Conventions and Constraints

- **Every Python product must have a `pyproject.toml`, `uv.lock`, and `.python-version`** — enforced implicitly by the root `make sync` / `make test` loops over `PYTHON_PRODUCTS` and by `make validate-version` checking `pyproject.toml` versions.
- **Dependencies must be declared as ranges, not exact pins**, in `pyproject.toml`; exact pins belong only in `uv.lock`. Adjudicated exceptions (e.g. keeping `redis<7.0`, `elasticsearch<9.0`) are documented in specs rather than ad hoc.
- **`uv sync --frozen` is the only supported way to install dependencies** in both dev and CI — loose resolution against PyPI is not used after the first lock.
- **Platform-wide version bumps require updating `VERSION` plus every product's `pyproject.toml` version and `metadata.py`** — `make validate-version` will fail the verification gate if any drift is detected.
- **Container images must be built from the shared `base-uv` image** and must `COPY pyproject.toml uv.lock` before running `uv sync --frozen --no-dev`, so the install layer is cacheable and reproducible.
- **No prerelease/beta/RC packages are adopted** anywhere in the backend or portal without an explicit spec exception (the recorded exception is OpenTelemetry instrumentation's permanent `0.xb` channel).
- **Policy bundles are treated as deploy-time configuration dependencies**: the canonical `policy-default.yaml` lives in `shared/platform-ops/gitops/dev-k8s/base/shared/` and is copied into consumers via `make sync-policy`; changes require bumping the bundle `version` field per SPEC-048 R-1.
