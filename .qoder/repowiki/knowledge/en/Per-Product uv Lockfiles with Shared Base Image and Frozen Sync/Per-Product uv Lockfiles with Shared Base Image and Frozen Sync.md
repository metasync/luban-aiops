## System Overview

The workspace uses **uv** (Astral) as the Python package manager across every product under `products/`. Each product is an independent PEP 621 project declared in its own `pyproject.toml`, with a committed `uv.lock` that pins every transitive dependency to exact versions and hashes. There is no monorepo-level virtualenv or shared `requirements.txt`; dependencies are managed per-product.

## Key Files and Packages

- Per-product manifests: `products/*/pyproject.toml` declare runtime dependencies, `[dependency-groups].dev` for test-only packages, and entry-point scripts under `[project.scripts]`.
- Per-product lockfiles: `products/*/uv.lock` — generated by uv, committed to version control, and consumed via `--frozen`.
- Interpreter pinning: each product has a `.python-version` file (e.g. `products/agent-platform/.python-version` = `3.12`) that tells uv which CPython interpreter to resolve and install.
- Shared base image: `shared/base-images/base-uv/Dockerfile` installs a pinned `uv` (`UV_VERSION=0.12.1`) on Amazon Linux 2023 minimal, sets environment variables (`UV_LINK_MODE=copy`, `UV_NO_SYNC=1`, `UV_PYTHON`, `UV_PYTHON_INSTALL_DIR=/app/.python`), and runs as non-root user `app` (uid 1000).
- Shared Makefile fragments: `mk/python.mk` provides `sync` and `test` targets that run `uv sync --frozen` and `uv run pytest`; `mk/image.mk` standardizes Docker build/push/lint targets used by every product.
- Root orchestrator: `Makefile` enumerates `PYTHON_PRODUCTS := agent-platform audit-service identity-broker incident-service platform-gateway skills-hub tool-gateway` and dispatches `make -C products/<name> sync|test` over all of them.
- Frontend dependency management (separate concern): `products/operator-portal/web-ui/package.json` + `package-lock.json` managed by npm.

## Architecture and Conventions

### Dependency declaration style
- Runtime dependencies use caret-style ranges (e.g. `fastapi>=0.115,<1.0`, `pydantic>=2.7,<3.0`) to allow patch/minor updates while blocking breaking major bumps.
- Dev-only dependencies live in `[dependency-groups].dev` (pytest, jsonschema, fakeredis) and are excluded from images via `--no-dev`.
- Extras are declared inline (e.g. `psycopg[binary]`, `uvicorn[standard]`).
- Build backend is pinned to `uv_build>=0.8.14,<0.9.0` in every product's `[build-system]`.

### Deterministic builds
- All development and CI paths invoke `uv sync --frozen`, which refuses to resolve against PyPI and instead installs exactly what `uv.lock` records.
- Container images copy only `.python-version`, `pyproject.toml`, `uv.lock`, and `src/` into the image, then run `uv sync --frozen --no-dev` — dev deps never ship to production.
- The shared base image pins `UV_VERSION=0.12.1` via a versioned installer URL (`https://astral.sh/uv/${UV_VERSION}/install.sh`); the strategy doc explicitly calls this out as the accepted supply-chain decision for this phase.
- `UV_NO_SYNC=1` is set in the base image so container entrypoints do not re-resolve at startup; the frozen env is baked in during `RUN uv sync --frozen --no-dev`.

### Version coordination
- A root `VERSION` file is the single source of truth for the platform release; `make validate-version` (via `shared/shared-contracts/scripts/validate_version.py`) enforces that every product's `pyproject.toml` version stays in lockstep with it.
- Coordinated image tagging: `make build` computes one `IMAGE_TAG` from `VERSION` + git SHA + optional profile and writes it into `shared/platform-ops/gitops/dev-k8s/.images.env`, which is then consumed by the GitOps overlay deploy.

### Policy and contract alignment
- Policy bundles are centralized in `shared/shared-contracts/policies/policy-default.yaml` and copied to consumers via `make sync-policy` (targeting `platform-gateway` and `tool-gateway` policy files plus the K8s overlay). This is analogous to how dependency versions are kept consistent across products.

## Conventions and Constraints

- **Every Python product must have a `pyproject.toml`, a `.python-version`, and a committed `uv.lock`.** Enforced by the shared `mk/python.mk` targets that assume these files exist and by the root `Makefile`'s loop over `PYTHON_PRODUCTS`.
- **Never run `uv sync` without `--frozen` in deterministic paths.** The shared Makefile, the container strategy doc, and all product Dockerfiles use `uv sync --frozen` (and `--no-dev` in images). The docs state this is required for reproducible builds.
- **Interpreter selection is explicit per product.** The base image has no system Python; uv resolves the interpreter from `.python-version`, with `UV_PYTHON` as a deterministic fallback. Changing the runtime requires updating `.python-version` and regenerating `uv.lock`.
- **Dependency ranges cap major versions.** Across all examined `pyproject.toml` files, runtime deps use `<X+1.0` upper bounds (e.g. `fastapi>=0.115,<1.0`, `pydantic>=2.7,<3.0`, `opentelemetry-sdk>=1.25,<2.0`), preventing accidental breaking upgrades.
- **Dev dependencies are isolated.** Test-only packages go in `[dependency-groups].dev` and are excluded from images via `--no-dev`; they are still installed locally by `make sync` / `make test` because those targets omit `--no-dev`.
- **No vendoring of third-party wheels.** Dependencies are resolved from PyPI (`registry = "https://pypi.org/simple"` in lockfiles); there is no local `vendor/` directory or private registry configured in the codebase.
- **Frontend assets are separate.** The operator portal uses npm (`package.json` + `package-lock.json`); it is not part of the uv-based Python dependency system.
