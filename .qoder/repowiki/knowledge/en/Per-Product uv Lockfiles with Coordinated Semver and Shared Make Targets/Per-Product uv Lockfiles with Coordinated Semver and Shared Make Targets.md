## System Overview

The Luban AIOps platform is a multi-product workspace (agent-platform, audit-service, identity-broker, incident-service, platform-gateway, skills-hub, tool-gateway, operator-portal) that manages dependencies through **per-product Python packages** using **uv** as the package manager, with each product declaring its own `pyproject.toml` and a committed `uv.lock` lockfile. The frontend operator portal uses **npm** (`package.json` + `package-lock.json`) under `products/operator-portal/web-ui/app/`. There is no monorepo-level dependency manifest — each product owns its dependency graph independently.

## Key Files

- Per-product manifests: `products/*/pyproject.toml` (Python), `products/operator-portal/web-ui/app/package.json` (Node)
- Per-product lockfiles: `products/*/uv.lock`, `products/operator-portal/web-ui/app/package-lock.json`
- Shared build helpers: `mk/python.mk`, `mk/image.mk`, `mk/defaults.mk`
- Root orchestrator: `Makefile` (aggregates `sync`, `test`, `build`, `push` across products)
- Version enforcement: `shared/shared-contracts/scripts/validate_version.py`, root `VERSION` file
- Build backend: `uv_build>=0.8.14,<0.9.0` declared in every Python product's `[build-system]`
- Runtime pinning: `.python-version` files per product (e.g. `products/agent-platform/.python-version`)

## Architecture & Conventions

### Python dependencies (uv)

- Every Python product declares `requires-python = ">=3.11"` and pins runtime via a per-product `.python-version` file.
- Dependencies are declared as version-ranged strings in `pyproject.toml` `dependencies` (e.g. `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`). Cross-product shared libraries (FastAPI, Pydantic, PyJWT, cryptography, httpx, opentelemetry-*, prometheus-client, uvicorn) use **aligned ranges** so all services stay compatible without a shared dependency file.
- Dev-only dependencies live in `[dependency-groups].dev` (pytest, jsonschema, fakeredis) and are excluded from production builds.
- Each product has its own `uv.lock` generated by `uv lock`; the root `mk/python.mk` target `sync` runs `uv sync --frozen`, which enforces that the lockfile must match exactly what is checked in — preventing drift between developer environments and CI.
- The root `Makefile` lists `PYTHON_PRODUCTS := agent-platform audit-service identity-broker incident-service platform-gateway skills-hub tool-gateway` and delegates `make sync` / `make test` to each product sequentially.

### Node.js dependencies (npm)

- The operator portal web UI is a standalone npm project under `products/operator-portal/web-ui/app/` with `package.json` and `package-lock.json`. It pins Node engine to `>=22` via `engines.node` and uses Vite + TypeScript + Vitest for build/test.
- No npm workspaces or monorepo tooling is used; it is treated as an independent product.

### Containerization ties

- Each product ships a `Dockerfile` built via `make -C products/<name> build`, which uses the shared `mk/image.mk` and `mk/defaults.mk` fragments. The root `Makefile` computes a coordinated `IMAGE_TAG` from the root `VERSION` file and writes image names into `shared/platform-ops/gitops/dev-k8s/.images.env`, ensuring all images share one tag.
- A shared base image `shared/base-images/base-uv/Dockerfile` is built first (`make base-images`) and passed `BASE_UV_UV_VERSION` / `BASE_UV_PYTHON_VERSION` build args, centralizing the uv and Python versions used inside containers.

### Version coordination (not just dependency versions)

- The root `VERSION` file is the single source of truth for the platform semver. `shared/shared-contracts/scripts/validate_version.py` (invoked via `make validate-version`) asserts that every `products/*/pyproject.toml [project] version`, every `src/*/metadata.py` `SERVICE_VERSION`, any `__version__` in package roots, and the operator portal's Vite config wiring all match this value. This is enforced as part of the `make verify` gate.

## Conventions & Constraints

1. **Per-product dependency ownership.** There is no shared `requirements.txt`, `Pipfile`, or monorepo lockfile. Each product's `pyproject.toml` is authoritative; cross-product compatibility is maintained by aligning version ranges manually (e.g. all services pin `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`, `opentelemetry-sdk>=1.25,<2.0`).
2. **Lockfiles are committed and frozen.** `uv sync --frozen` is used everywhere (in `mk/python.mk` and per-product Makefiles). Any change to dependencies requires regenerating the lockfile and committing it; otherwise `make sync` fails.
3. **No vendoring.** Dependencies are resolved from PyPI (`source = { registry = "https://pypi.org/simple" }` in lockfiles); there is no `vendor/` directory or private registry configured at the workspace level.
4. **Build-time isolation.** The `uv_build` backend (`requires = ["uv_build>=0.8.14,<0.9.0"]`) is used for all Python products, and the container base image pins the exact uv version via build args, so builds are reproducible regardless of the host uv installation.
5. **Dev vs prod separation.** Test-only packages (pytest, jsonschema, fakeredis) are placed in `[dependency-groups].dev` and are not installed in production images.
6. **Coordinated release versioning.** All products share the same semantic version from the root `VERSION` file, enforced by `make validate-version` (which calls `validate_version.py`). Drift causes the verification gate to fail.
7. **Shared policy bundles are synchronized, not versioned together.** Policy YAML files (`policy-default.yaml`) are copied from `shared/shared-contracts/policies/policy-default.yaml` into each consumer product via `make sync-policy`, keeping policy definitions in sync with code changes.
