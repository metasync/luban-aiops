## What system/approach is used

The repository uses **uv** (Astral's Python package manager) as the single dependency resolution and installation tool across all Python products. Each product under `products/` is an independent PEP 621 project declared in its own `pyproject.toml`, with a co-located `uv.lock` lockfile pinning every transitive dependency to exact versions and hashes. The build backend is `uv_build` (declared in each product's `[build-system]`). There are no `requirements.txt`, Poetry, pipenv, or vendored third-party packages — uv is the sole mechanism.

## Key files and packages

- Per-product manifests: `products/*/pyproject.toml` declare `[project]` dependencies, `[dependency-groups.dev]` for test-only packages, entry-point scripts under `[project.scripts]`, and `[build-system]` using `uv_build`.
- Per-product lockfiles: `products/*/uv.lock` — generated by uv, records exact resolved versions, sources (`registry = "https://pypi.org/simple"`), and wheel/sdist hashes for deterministic installs.
- Shared base image: `shared/base-images/base-uv/Dockerfile` installs a pinned `UV_VERSION=0.12.1` into Amazon Linux 2023 minimal, sets `UV_PYTHON=3.12`, `UV_LINK_MODE=copy`, `UV_NO_SYNC=1`, and runs as non-root user `app`.
- Product Dockerfiles (e.g. `products/agent-platform/Dockerfile`) copy `.python-version`, `pyproject.toml`, `uv.lock`, then run `uv sync --frozen --no-dev` inside the container.
- Per-product `.python-version` pins the interpreter (e.g. `3.12`).
- Shared Make fragments: `mk/python.mk` exposes `sync` (`uv sync --frozen`) and `test` (`uv sync --frozen && uv run pytest`) targets included by each product's Makefile.
- Root `Makefile` orchestrates cross-product operations: `PYTHON_PRODUCTS := agent-platform audit-service identity-broker incident-service platform-gateway skills-hub tool-gateway`; `make sync` iterates them; `make verify` runs tests, overlays, policy validation, and version lockstep checks.

## Architecture and conventions

- **Per-product isolation**: Each service owns its own `pyproject.toml` + `uv.lock`. Dependencies are not shared via a workspace-level `pyproject.toml`; instead, common libraries (FastAPI, Pydantic, OpenTelemetry, Prometheus, uvicorn, cryptography, httpx, PyJWT, PyYAML) are declared independently in multiple products with compatible version ranges so that uv resolves a consistent set across the monorepo.
- **Frozen installs everywhere**: Both local dev (`mk/python.mk`) and container builds use `uv sync --frozen`, which refuses to resolve against the network and requires the lockfile to be committed. This enforces reproducibility.
- **No dev deps in images**: Container builds pass `--no-dev` to `uv sync`, stripping test-only packages from production images.
- **Interpreter pinning**: Each product declares `requires-python = ">=3.11"` in `pyproject.toml` and a concrete `.python-version` file (`3.12`). The base image sets `UV_PYTHON=3.12` so uv picks that interpreter deterministically.
- **Public PyPI only**: All resolved packages source `https://pypi.org/simple`; there is no private registry, `pip.conf`, `PYPI_URL`, or `UV_INDEX_URL` configured anywhere in the repo.
- **Version ranges over exact pins**: `pyproject.toml` uses semver-compatible ranges (e.g. `fastapi>=0.115,<1.0`, `pydantic>=2.7,<3.0`, `agentscope>=2.0.4,<3.0`) to allow patch/minor updates while blocking breaking major releases. Exact pins live only in `uv.lock`.
- **Coordinated release via root `VERSION`**: The root `Makefile` reads `VERSION` and enforces that every product's `pyproject.toml` version matches it via `make validate-version` (runs `shared/shared-contracts/scripts/validate_version.py`). This is the single source of truth for the platform release number.

## Conventions and constraints

- Every Python product must have a `pyproject.toml` with PEP 621 metadata, a matching `uv.lock`, and a `.python-version` file — enforced by the fact that `make sync` / `make test` iterate `PYTHON_PRODUCTS` and fail if any product cannot `uv sync --frozen`.
- Dependency changes require updating both `pyproject.toml` (version range) and committing the regenerated `uv.lock`; the `--frozen` flag makes this a hard constraint for CI and containers.
- Dev/test-only dependencies go exclusively under `[dependency-groups.dev]` in `pyproject.toml` and are excluded from images via `--no-dev`.
- New services should follow the established layout: `src/<package>/`, `tests/`, `Dockerfile`, `Makefile` including `../../mk/python.mk`, and a `pyproject.toml` declaring runtime and dev dependencies.
- Policy configuration (separate from Python dependencies) is synchronized from `shared/shared-contracts/policies/policy-default.yaml` to consumer locations via `make sync-policy`, showing the same centralized-source pattern applied to config assets.
