## What system/approach is used

The Luban platform uses a **pure environment-variable configuration model** layered on top of Kubernetes ConfigMaps and Secrets, orchestrated through Kustomize overlays. There is no YAML/JSON config file consumed at runtime by services; every setting is read via `os.getenv` (or `os.environ.get`) from the process environment. A single authoritative cross-service reference lives in `docs/guides/configuration-reference.md`, which maps every capability to its required variables, defaults, and provisioning scripts.

Configuration is split into two layers:
- **runtime-config.env** per service under `shared/platform-ops/gitops/dev-k8s/base/<service>/runtime-config.env` — non-secret knobs mounted as a ConfigMap.
- **runtime-secrets.example.env** per service — secret keys that are generated by `sync-*.sh` scripts and injected via `secretKeyRef` or mounted files.

A third layer, **runtime profiles**, lives under `shared/platform-ops/gitops/runtime-profiles/`. Each profile is a Kustomize overlay that patches the agent-service's ConfigMap to select an LLM provider (`AGENTSCOPE_PROVIDER`, `AGENTSCOPE_MODEL_NAME`, `AGENTSCOPE_BASE_URL`). The active profile is selected at deploy time via `select-runtime-profile.sh`; base overlays like `browser-dev` and `mutating-dev` permanently merge feature flags alongside the active profile.

Secrets are never committed to Git. Dedicated scripts under `shared/platform-ops/gitops/sync-*.sh` generate random shared secrets (or reuse exported values) and write the resulting Kubernetes `Secret` objects: `sync-delegation-secrets.sh`, `sync-audit-secrets.sh`, `sync-skills-secrets.sh`, `sync-incident-secrets.sh`, `sync-execution-signing-secret.sh`, `sync-execution-handoff-secret.sh`, `sync-browser-credentials.sh`, `sync-otel-secrets.sh`, `sync-runtime-secret.sh`, `sync-sessions-db.sh`, `sync-incidents-db.sh`, `sync-identity-secrets.sh`.

## Key files and packages

- `products/agent-platform/src/agent_service/runtime_settings.py` — the canonical settings dataclass for agent-service; `RuntimeSettings.from_env()` parses ~50+ env vars, validates ranges in `__post_init__`, and exposes typed provider options (`DashScopeOptions`, `DeepSeekOptions`, `OpenAIOptions`).
- `products/*/src/*_service/core/config.py` — each other service mirrors this pattern: a frozen dataclass with `from_env()` reading `AUDIT_*`, `GATEWAY_*`, `IDENTITY_*`, `INCIDENT_*`, `SKILLS_*`, `EXECUTION_*` variables.
- `docs/guides/configuration-reference.md` — definitive variable dependency map, cross-service chains (token delegation, audit ingestion, skills retrieval, incident intake), policy rollout workflow, and per-service tables.
- `shared/platform-ops/gitops/dev-k8s/base/<service>/runtime-config.env` — per-service non-secret defaults for dev-k8s.
- `shared/platform-ops/gitops/runtime-profiles/default/configmap.yaml` — selects the active LLM provider/model.
- `shared/platform-ops/gitops/runtime-profiles/browser-dev/`, `mutating-dev/` — permanent feature-flag overlays merged into every deployment.
- `shared/platform-ops/gitops/sync-*.sh` — secret-provisioning scripts referenced throughout the configuration reference.

## Architecture and conventions

1. **One source of truth per service**: each product has exactly one `core/config.py` (or `runtime_settings.py`) whose `from_env()` classmethod is the single entry point for loading configuration. Services do not import `.env` files or parse CLI args for configuration.
2. **Typed validation at startup**: every numeric and boolean setting is parsed through helpers (`_optional_int`, `_optional_float`, `_optional_bool`, `_optional_choice`) and validated in `__post_init__`, raising `ValueError` with explicit messages tied to SPEC numbers (e.g. `AGENTSCOPE_MAX_ITERS must be >= 1`, `AGENTSCOPE_CONTEXT_TRIGGER_RATIO must be in the open interval (0, 0.9)`).
3. **Fail-closed by default**: unset optional dependencies degrade gracefully (audit emission falls back to log-only; missing `*_SERVICE_URL` leaves routes returning 503); but critical security knobs fail startup or reject operations (unsupported `AGENTSCOPE_PROVIDER`, invalid IANA timezone, missing `AGENT_EXECUTION_SIGNING_KEY` rejects mutating resumes with `signing_unavailable`).
4. **Cross-service secret contracts**: inter-service authentication is modeled as matching pairs of client_id/client_secret entries in registries (`AUDIT_INGEST_CLIENTS`, `SKILLS_QUERY_CLIENTS`, `INCIDENT_QUERY_CLIENTS`, `IDENTITY_SERVICE_CLIENTS`). The configuration reference documents each chain with ASCII diagrams showing which variables must match across pods.
5. **Policy bundle is immutable at runtime**: the single canonical file `shared/shared-contracts/policies/policy-default.yaml` is synced byte-identically to both gateways' packaged defaults and the dev-k8s overlay via `make sync-policy`; consumers load it from a configured path and refuse to start if it is missing or invalid.
6. **Profile-based LLM selection**: the agent-service supports multiple providers (`dashscope`, `deepseek`, `openai`, `luban`) selected via `AGENTSCOPE_PROVIDER` in a profile ConfigMap; additional models can be registered via `<PROVIDER>_API_KEY` / `<PROVIDER>_MODEL_NAME` / `<PROVIDER>_BASE_URL` / `<PROVIDER>_MODELS`.
7. **Feature toggles are environment-driven**: capabilities like browser web-checks (`GATEWAY_BROWSER_ENABLED`), HTTP checks (`GATEWAY_HTTP_ENABLED`), mutating tools (`GATEWAY_MUTATING_TOOLS_ENABLED`), live model discovery (`AGENT_MODEL_DISCOVERY_ENABLED`), and kernel tracing (`AGENTSCOPE_KERNEL_TRACING`) are all opt-in via env vars, documented in the Feature Activation Matrix table.

## Conventions and constraints

- **All configuration comes from environment variables**; no file-based config is loaded at runtime by any service.
- **Secrets are provisioned exclusively through `sync-*.sh` scripts** and injected as Kubernetes Secrets — never committed to Git. The configuration reference explicitly states "Secrets are provisioned as Kubernetes Secret objects, never committed to Git."
- **Each capability has a Feature Activation Matrix row** listing required variables, affected services, and dev-k8s defaults; adding a new feature requires updating this table.
- **Cross-service credentials use a registry pattern**: a central service (audit-service, skills-hub, incident-service, identity-service) holds a `*_CLIENTS` or `*_QUERY_CLIENTS` string of `client_id=secret,...` entries; callers register their own `*_CLIENT_ID` + `*_CLIENT_SECRET` that must match.
- **Policy changes follow a strict workflow**: edit `policy-default.yaml`, bump its `version`, update `policy-scenarios.yaml`, run `make sync-policy`, verify with `make verify`, then deploy — there is no hot reload; changed ConfigMaps take effect on pod restart.
- **Dev vs production posture**: dev-k8s enables features like kernel tracing (`AGENTSCOPE_KERNEL_TRACING=true`) and http.get auto-allow (`AGENT_GATEWAY_TOOL_AUTO_ALLOW_EXTRA=http.get`) via comments explaining why they differ from production defaults; production deployments should not rely on these dev overrides.
- **Timezone validation**: `AGENTSCOPE_TIMEZONE` must be a valid IANA timezone name, validated at startup via `zoneinfo.ZoneInfo`.
- **Provider options are type-checked against the active provider**: `provider_options_type(self.provider)` ensures `DashScopeOptions`, `DeepSeekOptions`, or `OpenAIOptions` match `AGENTSCOPE_PROVIDER`, raising a `ValueError` on mismatch.
