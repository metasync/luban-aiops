- Specs use a fixed top-level section order (Status → Summary → Motivation → Requirements with numbered R-N blocks → Design Decisions → Non-Goals → Impact → Open Questions → Changelog) so reviewers can scan consistently across SPEC-015, SPEC-043, and SPEC-045.
- Every requirement carries testable acceptance criteria written as bullet points enumerating endpoint behavior, status codes, error shapes, and integration boundaries rather than prose descriptions.
- Cross-product contracts are pinned to concrete file paths (e.g. `shared/shared-contracts/schemas/incident.schema.json`, `triage-report.schema.json`, `operation-document.schema.json`) and enforced via contract tests binding Pydantic models to those schemas.
- New policy actions follow the deny-by-default pattern: a single new verb (e.g. `incident:triage`, `incident:skill_draft`) is added alongside existing `incident:read`/`incident:create` and documented in both `policy-default.yaml` and the dev-k8s `policy.yaml`.
- External collaboration or downstream integrations are modeled as a pluggable `Connector` protocol with a registry selected via a comma-separated env var, keeping third-party adapters out of the release boundary while preserving a documented extension point.
- Generation paths degrade deterministically instead of raising 500s: missing prerequisites return structured 4xx (e.g. 409 no validated triage report), unavailable dependencies return 503/502, and LLM failures fall back to a facts-only skeleton.
