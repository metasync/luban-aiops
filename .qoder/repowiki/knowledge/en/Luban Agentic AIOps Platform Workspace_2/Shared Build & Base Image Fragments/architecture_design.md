Two cooperating concerns live under this scope:
- `mk/` contains three include-only Makefile fragments consumed by product Makefiles via `include ../../mk/<fragment>.mk`. `defaults.mk` is the single source of truth for overridable build variables (image platform, tag prefix/profile, registry, kind auto-load, and base-image pins) guarded by an `ifndef LUBAN_DEFAULTS_INCLUDED` double-inclusion guard. `image.mk` defines the shared `build`, `push`, and `lint` targets that wrap `docker build`/`tag`/`push` against `IMAGE_NAME`/`IMAGE_CONTEXT`/`IMAGE_DOCKERFILE`, with `hadolint` as the preferred Dockerfile linter falling back to a docker-run invocation. `python.mk` adds `sync` and `test` targets that run `uv sync --frozen` and `uv run pytest` with OTLP exporters disabled so tracing tests can keep the SDK active.
- `shared/base-images/base-uv/Dockerfile` builds the shared base image (`luban-aiops/base-uv`) on top of `public.ecr.aws/amazonlinux/amazonlinux:2023-minimal`, pinning `uv` and Python versions via `ARG`s, installing only `curl-minimal` plus minimal runtime deps, creating a non-root `app` user (uid 1000), and setting `UV_LINK_MODE=copy`, `UV_NO_SYNC=1`, and `UV_PYTHON_INSTALL_DIR=/app/.python` so each product resolves its interpreter from `.python-version` during `uv sync`.
Dependency direction is one-way: product Makefiles include these fragments; the base image has no dependencies on product code. All pins flow from `mk/defaults.mk` into the base image build via `--build-arg` overrides.
