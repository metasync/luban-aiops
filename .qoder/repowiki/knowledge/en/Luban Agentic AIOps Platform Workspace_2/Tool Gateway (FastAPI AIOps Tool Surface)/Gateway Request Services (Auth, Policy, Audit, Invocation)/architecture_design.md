The module is organized as four cooperating service modules that together implement one request lifecycle inside the FastAPI gateway:
- `gateway_service.py` is the orchestrator entry point. It exposes `resolve_request_identity`, `enforce_policy`, and `invoke_tool`, which chain identity resolution → policy check (`tools:invoke`, then `tools:mutate` for non-read tools) → registry dispatch → redaction → audit logging.
- `policy_engine.py` implements a small, dependency-free action-based authorization engine. It loads a YAML bundle (from an optional filesystem path or the packaged default `policy-default.yaml`) into a module-level singleton cache keyed by configured path, computes a SHA-256 fingerprint exposed via `bundle_sha256()` for readiness probes, and evaluates actions against rules with a strict precedence: explicit deny > require_approval > allow > deny-by-default. `require_approval` rules are parsed but skipped at load time because this gateway has no approval substrate (SPEC-030 R-2).
- `token_verifier.py` performs local JWT verification using PyJWT's `PyJWKClient` against a JWKS endpoint; it caches the client per configured URL and raises a domain `TokenVerificationError` with specific detail strings consumed by the caller to record metrics.
- `audit_emitter.py` builds audit envelopes matching the shared-contracts schema and delivers them asynchronously on a daemon thread over HTTP to `/api/v1/audit/events` with a 2-second timeout; failures are swallowed so the audit service can never degrade the tool path (SPEC-013 R-3).

Dependency direction is strictly inward: `gateway_service` depends on all three peers; `policy_engine`, `token_verifier`, and `audit_emitter` depend only on `core.config`, `schemas.api`, `core.metrics`, and `core.observability`. Cross-cutting concerns (metrics, observability logs, settings) are injected rather than imported from sibling packages.
