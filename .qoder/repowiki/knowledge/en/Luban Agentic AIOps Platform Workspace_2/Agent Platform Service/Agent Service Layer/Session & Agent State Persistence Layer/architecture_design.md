Three cooperating files form a layered persistence boundary:
- `session_service.py` is the stateless service facade exposing `create_session`, `create_named_session`, `ensure_session`, `get_session`, `rename_session_title`, `list_sessions`, `mark_session_turn`, `pin_session_model`, and `delete_session`. It enforces ownership via `_assert_session_owner` (foreign user IDs are mapped to 404 for anti-enumeration), applies prose redaction before title minting, and coordinates cascading deletes across sibling stores (`AGENT_STATE_STORE`, `EVIDENCE_STORE`, `CONFIRMATION_RECORD_STORE`, `EXECUTION_RECORD_STORE`, `AUTHORING_TRACE_STORE`, plus in-memory `FLOW_CONTEXTS`/`FLOW_APPROVALS`).
- `session_store.py` defines a `SessionStore` Protocol and three implementations: `InMemorySessionStore` (TTL + max-entry eviction), `RedisSessionStore` (JSON blobs with TTL, sorted-set user index, atomic NX-minted titles on a separate key), and `PostgresSessionStore` (DDL-managed `sessions` table with idle-TTL refresh folded into reads). A module-level `SESSION_STORE` singleton is built by `build_session_store()` which selects the backend via `SESSION_STORE_BACKEND` env var and falls back to memory when Postgres is unreachable.
- `agent_state_store.py` mirrors the same pattern for kernel snapshots: an `AgentStateStore` Protocol with `InMemoryAgentStateStore` and `PostgresAgentStateStore` (separate `agent_states` table, JSONB payload), selected by `AGENT_STATE_STORE_BACKEND` and exposed as the `AGENT_STATE_STORE` singleton.
Dependency direction is strictly downward: service → store Protocol → concrete backend; backends never import the service. Both backends record metrics via `core.metrics` and use per-operation connection contexts so failures degrade gracefully without failing the caller.
