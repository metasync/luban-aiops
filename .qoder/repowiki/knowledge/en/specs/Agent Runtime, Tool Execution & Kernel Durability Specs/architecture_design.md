Three sibling spec documents (SPEC-002, SPEC-007, SPEC-017) form a cohesive R1 delivery slice around the AgentScope runtime:
- SPEC-002 establishes the platform-owned HTTP+SSE boundary at `/api/v2/` in `agent-platform`, replacing the dual FastAPI adapter + native AgentScope surface; `tool-gateway` becomes a pure consumer of this contract, with JSON Schema files living under `shared/shared-contracts/schemas/` (`agent-chat-request`, `agent-chat-response`, `agent-stream-event`, `agent-session`, `agent-runtime-metadata`, `agent-health`).
- SPEC-007 builds on that contract by adding the tool-execution layer: `tool-invocation.schema.json` / `tool-result.schema.json` define the wire format, `ToolRegistry` + `BaseTool` provide an in-process registry in `tool-gateway`, the first connector is read-only Kubernetes (`k8s.list_pods`, `get_pod`, `get_events`, `get_pod_logs`) gated by `GATEWAY_K8S_ENABLED`, and `agent-platform`'s `RuntimeSettings.tool_gateway_url` drives dynamic toolkit registration via `GET /api/v2/tools`.
- SPEC-017 deepens the kernel integration: new `RuntimeSettings` knobs (`AGENTSCOPE_MAX_ITERS`, `CONTEXT_TRIGGER_RATIO`, `TOOL_RESULT_LIMIT`, `TIMEZONE`, `MODEL_MAX_RETRIES`) map to AgentScope's `ReActConfig`/`ContextConfig`/`InjectionConfig`/`ModelConfig`; structured output replaces fenced-JSON triage reports; an `AgentStateStore` protocol (in-memory default, Postgres backend selected by `AGENT_STATE_STORE_BACKEND`) snapshots `AgentState.model_dump_json()` keyed by session id after every completed turn, with fail-open fallback to memory.
Dependency direction is one-way: specs reference each other (SPEC-007 depends on the contract from SPEC-002; SPEC-017 pairs with SPEC-016 for sessions DB), but they are documentation artifacts — implementation lives in `products/agent-platform`, `products/tool-gateway`, and `shared/shared-contracts`.
