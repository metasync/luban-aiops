Three independent but sequentially layered spec documents, each following the same `plan.md` / `spec.md` / `tasks.md` triad and sharing a common contract surface in `shared/shared-contracts`:
- SPEC-004 introduces deny-by-default authorization at the gateway: a pure in-memory policy engine evaluates versioned YAML bundles (loaded from `GATEWAY_POLICY_PATH`, falling back to a packaged default) against role→action rules (`policy-rule.schema.json`) and emits structured decisions (`policy-decision.schema.json`). The decision module lives inside the gateway; the schema contract is product-neutral in shared-contracts so it can later be lifted behind a policy-center service.
- SPEC-030 extends that contract with a third outcome `require_approval` carrying an explicit `approval.tier` (`tier_1` self-confirmation allowed, `tier_2` requires a distinct designated approver). Both gateway engines evaluate it with precedence `deny > require_approval > allow`; platform-gateway bridges the requirement onto the existing `chat:confirm` path while tool-gateway validates but skips the rule. Default bundle posture and portal matrix/confirmation-card rendering are additive changes on top of the SPEC-021/020 substrate.
- SPEC-037 closes the R4 slice by adding HMAC-SHA256-signed execution envelopes around approved tool calls: agent-service constructs a request at resume (fail-closed if signing key is absent), tool-gateway verifies the argument digest at invocation, and both sides persist request/receipt records keyed by `confirm_id`+`call_id` alongside the SPEC-031 confirmation store, emitting new audit events (`execution_requested`, `execution_completed`, `execution_rejected`).
Dependency direction is strictly forward: SPEC-030 extends SPEC-004's contract; SPEC-037 builds on the approval substrate from SPEC-030/031 without altering tiers or pending-record behavior. All three specs target additive schema revisions in shared-contracts and gate deployment via `make sync-policy` / `make validate-policy` plus CI test suites per product.
