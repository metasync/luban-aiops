## Approach

The Luban workspace is a monorepo of independently containerized Python services. Dependency management is handled exclusively by **uv** (the fast Python package manager), one `pyproject.toml` + `uv.lock` pair per product under `products/<name>/`. There are no `requirements.txt`, `Pipfile`, `setup.py`, or vendored third-party packages.

The operator-portal SPA (`products/operator-portal/web-ui/app/package.json`) uses npm for its Node/React dependencies, but the rest of the platform is uv-only.

## Key files

- Root orchestrator: `Makefile` — declares `PYTHON_PRODUCTS := agent-platform audit-service execution-runtime identity-broker incident-service platform-gateway skills-hub tool-gateway` and delegates `sync` / `test` to each product's Makefile.
- Shared uv targets: `mk/python.mk` — defines `sync` and `test`; both call `uv sync --frozen` so every install is resolved from the locked file.
- Per-product manifests: `products/*/pyproject.toml` declare `[project]` dependencies with upper-bound pinning (e.g. `agentscope>=2.0.4,<3.0`, `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`).
- Per-product lockfiles: `products/*/uv.lock` — generated by uv; committed alongside the manifest.
- Build backend: every Python product pins `build-system.requires = ["uv_build>=0.8.14,<0.9.0"]` with `build-backend = "uv_build"`.
- Node frontend: `products/operator-portal/web-ui/app/package.json` (npm) with an `engines.node >= 22.22.2` constraint.

## Architecture and conventions

1. **One uv project per service.** Each product in `products/` is self-contained: it has its own `.python-version`, `Dockerfile`, `Makefile`, `pyproject.toml`, and `uv.lock`. The root `Makefile` never resolves Python dependencies itself — it loops over `$(PYTHON_PRODUCTS)` and runs `make -C products/$$p sync`.

2. **Frozen installs everywhere.** `mk/python.mk` invokes `uv sync --frozen` for both development sync and test execution. This means the lockfile is authoritative: any drift between `pyproject.toml` and `uv.lock` fails the build rather than silently re-resolving.

3. **Upper-bound version ranges.** Dependencies use caret-style ranges that allow patch/minor updates but cap at the next major version (e.g. `agentscope>=2.0.4,<3.0`, `redis>=6.2,<7.0`, `psycopg[binary]>=3.2,<4.0`). This is a deliberate convention visible across all `pyproject.toml` files.

4. **Dev vs runtime separation via dependency-groups.** Runtime deps live under `[project].dependencies`; test/dev-only deps (pytest, fakeredis, jsonschema) go under `[dependency-groups].dev`. The root `verify` gate does not install dev groups during image builds — only the `sync` target used by developers/tests does.

5. **Base image pins uv and Python versions.** `shared/base-images/base-uv/Dockerfile` plus `mk/defaults.mk` define `BASE_UV_UV_VERSION` and `BASE_UV_PYTHON_VERSION`; the root `base-images` target passes them as `--build-arg UV_VERSION` / `PYTHON_VERSION` when building the shared base image. This ensures CI and local containers resolve against the same uv binary.

6. **No private registry configuration in this repo.** No `PIP_INDEX_URL`, `UV_INDEX_URL`, `PYPI_TOKEN`, or `pip.conf` is checked in. Third-party packages are pulled from PyPI (and npm registry for the SPA). Private registries would be configured outside the repo (e.g. via CI secrets or container registry mirrors).

7. **Lockstep versioning enforced by scripts.** `make validate-version` runs `shared/shared-contracts/scripts/validate_version.py` against the repo root to keep the root `VERSION` file in sync with every product's declared version. This is a cross-cutting invariant enforced at verify time.

## Conventions and constraints

- **Convention:** All Python dependencies are declared in `pyproject.toml` using `>=X.Y,<Z.0` ranges; there are no exact pins in manifests — pins live in `uv.lock`.
- **Convention:** Dev/test dependencies are isolated in `[dependency-groups].dev`; runtime images do not install them.
- **Enforced rule:** `uv sync --frozen` is the only supported way to install dependencies (see `mk/python.mk`); non-frozen installs are not exposed through any Make target.
- **Enforced rule:** Every Python product must include `build-system.requires = ["uv_build>=0.8.14,<0.9.0"]` and `build-backend = "uv_build"` (observed in all `products/*/pyproject.toml`).
- **Enforced rule:** The root `make verify` target calls `make -C products/$$p test` for each Python product, which internally runs `uv sync --frozen` before pytest, so tests cannot pass without a valid lockfile.
- **Enforced rule:** The coordinated image tag is derived from the root `VERSION` file and propagated to every product image via `IMAGE_TAG` (root `Makefile` lines 100–113), keeping service versions aligned.
- **Constraint:** No vendoring strategy exists; third-party code is always fetched from remote registries at build time.
