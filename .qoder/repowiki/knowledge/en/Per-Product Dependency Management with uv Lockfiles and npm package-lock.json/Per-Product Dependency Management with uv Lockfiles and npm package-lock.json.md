## System

The Luban Agentic AIOps Platform Workspace uses two package managers, one per language surface:

- **Python**: `uv` (PEP 621 via `pyproject.toml`, deterministic resolution via per-product `uv.lock`).
- **Frontend (operator portal SPA)**: `npm` (`package.json` + `package-lock.json` under `products/operator-portal/web-ui/app/`).

There is no monorepo workspace tool (no `pnpm-workspace.yaml`, no `pip-tools`/`poetry.lock`, no `Cargo.toml`, no `go.mod`). Each product in `products/<name>/` is an independent Python distribution; the operator portal's web UI is an independent npm project.

## Key files

- Per-product Python manifests and lockfiles: `products/*/pyproject.toml`, `products/*/uv.lock`, `products/*/.python-version`.
- Shared build fragments: `mk/python.mk` (the only place `uv sync --frozen` and `uv run pytest` are invoked), `mk/image.mk`, `mk/defaults.mk`.
- Root orchestrator: `Makefile` — declares `PYTHON_PRODUCTS := agent-platform audit-service execution-runtime identity-broker incident-service platform-gateway skills-hub tool-gateway` and runs `sync` / `test` across them.
- Frontend manifest: `products/operator-portal/web-ui/app/package.json` (with `engines.node >=22.22.2`).
- Policy document: `docs/specs/SPEC-042-dependency-hygiene/spec.md` (delivered as v0.24.0) plus its release note `docs/agentic-aiops-platform/release-notes/2026-08-28-dependency-hygiene.md`.
- Shared base image definition: `shared/base-images/base-uv/Dockerfile` (pinned `UV_VERSION` and `PYTHON_VERSION` build args).

## Architecture and conventions

### Python products

Each Python product follows a uniform layout: `src/<package>/`, `tests/`, `Dockerfile`, `Makefile`, `pyproject.toml`, `uv.lock`, `.python-version`. Dependencies are declared in `[project.dependencies]` of `pyproject.toml` using PEP 508 version ranges (e.g. `agentscope>=2.0.4,<3.0`, `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`). Development-only dependencies live under `[dependency-groups].dev` (e.g. `fakeredis`, `pytest`). The build backend is pinned to `uv_build>=0.8.14,<0.9.0`.

Resolution and installation are always performed through `make -C products/<name> sync`, which delegates to `mk/python.mk` and executes `uv sync --frozen`. This means the committed `uv.lock` is authoritative — dependency resolution is not allowed to float at install time. The root `make sync` iterates over all eight Python products and fails fast on the first failure.

Tests are executed via `uv run pytest` inside the frozen environment, with OpenTelemetry exporters disabled (`OTEL_TRACES_EXPORTER=none OTEL_METRICS_EXPORTER=none OTEL_LOGS_EXPORTER=none`) so test output stays clean while the SDK remains active for tracing tests.

### Frontend

The operator portal SPA lives under `products/operator-portal/web-ui/app/` and uses `vite` + `vitest` + `typescript` + `react` + `antd`. Dependencies are declared in `package.json`; the resolved tree is captured in `package-lock.json`. The `build` script runs `tsc --noEmit && vite build`, and the `test` script runs `vitest run`. Node engine floor is `>=22.22.2` (matching jsdom 30's requirement).

### Base image pinning

The shared `base-uv` image is built from `shared/base-images/base-uv/Dockerfile` and exposes `BASE_UV_UV_VERSION`, `BASE_UV_PYTHON_VERSION`, and `BASE_UV_TAG` variables (defined in `mk/defaults.mk`). The root `make base-images` passes these as `--build-arg`s, ensuring every product container is built against the same uv and Python versions.

### Version coordination

The root `VERSION` file is the single source of truth for the platform release version. The root `Makefile` includes `validate-version` (via `shared/shared-contracts/scripts/validate_version.py`) which asserts that `VERSION`, each product's `__version__` / metadata, and the portal are kept in lockstep. This is part of the `make verify` gate.

## Conventions and constraints

- **Frozen installs everywhere.** `mk/python.mk` invokes `uv sync --frozen` for both `sync` and `test`; there is no unfrozen path in the shared Makefile targets. The root `Makefile` also uses `uv run --frozen` for integration test scripts (e.g. `audit-contract-test`, `delegated-custody-test`).
- **Latest stable only policy.** SPEC-042 codifies the adoption rule: "adopting latest stable versions only" — no alpha, beta, RC, or dev builds. The sole recorded exception is the OpenTelemetry instrumentation packages, which ship upstream on a permanent `0.xb` channel and stay at their locked SDK pairing rather than chasing newer betas.
- **Version ranges use upper bounds.** Python dependencies consistently cap major versions (e.g. `<3.0`, `<1.0`, `<4.0`, `<7.0`) to prevent accidental major upgrades. Some caps are deliberate and documented (redis `<7.0`, elasticsearch `<9.0` parked because client majors follow server majors); others were raised after call-site review (cryptography raised from `<45.0` to `<51.0` after reviewing JWT/signing usage).
- **No vendoring.** There is no `vendor/` directory, no `requirements.txt` with hashes, no private registry configuration (`PIP_INDEX_URL`, `PYPI_MIRROR`, `UV_INDEX_URL`) found in the repository. Dependencies resolve directly from PyPI/npm registries.
- **Per-product lockfiles, not a workspace lock.** Each Python product owns its own `uv.lock`; there is no top-level lockfile aggregating all products.
- **Lockfile refreshes are spec-driven.** Major dependency updates are tracked as specs (SPEC-042 is the canonical example). Refreshes require re-running `uv lock` inside declared ranges, regenerating `uv.lock`, and passing `make verify` (all eight product suites green under frozen sync).
- **Node engine floor is enforced by the Dockerfile.** The portal's `engines.node >=22.22.2` is matched by the node base image used in the Dockerfile; SPEC-042 R-3 requires the Dockerfile's node base to satisfy the strictest adopted requirement.
- **Verification gate enforces consistency.** `make verify` aggregates product tests, overlay rendering, dashboard validation, policy validation, version lockstep checks, secret vocabulary validation, password-policy validation, portal unit/build, and delegated-custody/runtime/multi-process/edge integration tests. Any dependency change must pass this full gate.
- **Deprecation guard for antd.** The portal's vitest setup intercepts `console.error`/`console.warn` and fails the suite at teardown on any `[antd: …] … deprecated` warning — zero-tolerance, no allow-list. This is the enforcement mechanism for keeping the frontend stack current.
