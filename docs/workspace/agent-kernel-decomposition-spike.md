Status: proposal — read-only assessment plus a staged, behavior-preserving plan. **Stage 1 authorized to begin 2026-11-15** and executed (commit `cdac445a`); **Stage 2 authorized and executed 2026-11-15**; **Stage 3 authorized and executed 2026-11-16** — all by the operator as internal refactors (no contract, schema, policy, audit, or trust-model change). This memo authorizes no feature work and no spec promotion.
Date: 2026-11-15
Roadmap home: code-modularity track opened by the v0.58.1 code & document review (finding C-1); no Exploration Backlog row yet — promote to one only if the refactor is scheduled beyond Stage 1
Verified against: `products/agent-platform/src/agent_service/runtime_kernel.py` at v0.58.1 (static inspection: 3,393 LOC; `AgentKernel` spans L246→EOF, 76 methods); the extraction pattern in `services/kernel_middleware.py`; the agent-platform suite (1,793 tests) and the SPEC-063 `execution-failure-test` campaign (795)

## 1. Question

`AgentKernel` is the largest single concentration of responsibility in the platform — a ~3,150-line class with 76 methods, roughly 13% of the 24k-LOC agent-platform product in one type. Should it be decomposed; if so, along which seams, in what order, and behind what safety gate?

## 2. Findings — measured state (verified)

- **It is an orchestration concentration, not a state god-object.** `__init__` (L247) holds only three in-memory caches (`_agents`, `_toolkits`, `_generated_literals`), two `asyncio.Lock`s, and `settings` / `_provider` / `_last_error` / `_mutating_tools_excluded` / `_recovery`. All durable persistence is already delegated to eight module-level store/registry singletons (`AGENT_STATE_STORE`, `EVIDENCE_STORE`, `CONFIRMATION_REGISTRY`, `EXECUTION_RECORD_STORE`, `AUTHORING_TRACE_STORE`, `CONFIRMATION_RECORD_STORE`, `FLOW_APPROVALS`, `FLOW_CONTEXTS`). Decomposition means splitting *coordination* responsibilities, not untangling state.
- **The extraction pattern is already proven in-tree.** `services/kernel_middleware.py` pulls the cross-cutting concerns (permission gating, tool-evidence, target-authorization, token usage) out as agentscope `MiddlewareBase` subclasses; the kernel only *assembles* them (`_build_middlewares`, L733). New collaborators should follow the same "kernel assembles, collaborator executes" shape.
- **`_ensure_toolkit` (L502) is already a named seam** — SPEC-073/076 narrow the toolkit "at the `_ensure_toolkit(read_only=True)` seam," so a `ToolkitAssembler` extraction formalizes a boundary the specs already name.
- **Two monster methods are ~20% of the file:** `_resume_confirmation` (L2965–3322, ~357 lines) and `stream_events` (L1407–1724, ~317 lines); then `_build_confirmation_frame` (~173), `_sign_flow_execution` (~148), `_prepare_executions` (~140). Splitting a 350-line method is a readability/testability win even before any class extraction.

## 4. Options weighed

| Option | Shape | Cost | Risk | Verdict |
|---|---|---|---|---|
| A. Do nothing | status quo | none | growing maintainability drag; two methods = ~20% of the file | baseline |
| B. Split the monster methods in place | break `_resume_confirmation` / `stream_events` into named private helpers; no class moves | low | low — same class, same contextvars, byte-identical output | cheap 80/20; fold into Stage 4 or run standalone |
| C. Staged collaborator extraction | pull cohesive clusters into collaborators behind thin delegators | medium, multi-stage | medium — contextvar propagation + signature-path parity | **recommended; Stage 1 authorized** |
| D. Rewrite the kernel | clean-slate redesign | high | high — highest blast radius, no incremental safety | rejected |

## 5. Recommended plan — staged, behavior-preserving, verify-gated

Every stage is one commit, keeps behavior byte-identical, and runs the full agent-platform suite plus `make verify` (incl. the 795-test SPEC-063 campaign) before landing.

- **Stage 0 (prerequisite) — characterization gate.** Confirm the status / toolkit / stream / confirmation / execution paths are pinned by golden-output characterization tests; add focused ones where the existing suite leaves a gap. No refactor proceeds without this.
- **Stage 1 (low risk) — `KernelStatus` + `ToolkitAssembler`.** Extract the 12 read-only status projections and the 8 toolkit-assembly / role-narrowing methods into collaborators; keep thin delegating methods on `AgentKernel` so the public surface consumed by `api/v2/routes.py` is unchanged. **Done** (commit `cdac445a`): `services/kernel_status.py` + `services/kernel_toolkits.py`; `runtime_kernel.py` 3,393 → 3,146 LOC; adds `tests/test_kernel_stage1_characterization.py` (14 pins); suite 1,807 green.
- **Stage 2 (med) — `ModelResolver` + `AgentRegistry`.** Model selection (SPEC-024/026/027/071) and the agent build / cache / restore / snapshot lifecycle (owns `_agents` + `_agent_lock`). **Done 2026-11-15**: `services/kernel_models.py` (`ModelResolver`) + `services/kernel_agents.py` (`AgentRegistry`); `runtime_kernel.py` 3,146 → 2,916 LOC; adds `tests/test_kernel_stage2_characterization.py` (17 pins); suite 1,824 green. Behavior byte-identical: the persisted-state store binding (`AGENT_STATE_STORE`) is resolved through `runtime_kernel` at call time — not a module-level import in the collaborator — so the long-standing `monkeypatch.setattr(runtime_kernel, "AGENT_STATE_STORE", …)` test surface stays authoritative after the move.
- **Stage 3 (med-high) — `ExecutionDispatcher`.** The signed-request / receipt / ledger path (SPEC-037/063/077). Signature canonicalization must stay byte-identical or execution-runtime verification breaks; golden-output parity is mandatory. **Done 2026-11-16**: `services/kernel_executions.py` (`ExecutionDispatcher`, owns the `_recovery` / `_recovery_built` slot); moves the recovery / run-identity / `RunGuard` triad plus `_prepare_executions`, `_persist_execution_request`, `_sign_flow_execution`, `_execution_duration_ms`, `_emit_execution_event`; `runtime_kernel.py` 2,916 → 2,645 LOC; adds `tests/test_kernel_stage3_characterization.py` (10 pins); suite 1,834 green. Byte-parity held: the crypto / canonicalization core stays in `execution_signing.py` (imported by identity, untouched); `emit_audit_event` is resolved through `runtime_kernel` at call time — not a module-level import in the collaborator — so the `monkeypatch.setattr("agent_service.runtime_kernel.emit_audit_event", …)` surface stays authoritative (the same hazard class Stage 2 hit with `AGENT_STATE_STORE`); and sibling execution calls route back through the kernel, so instance-level monkeypatches (`_execution_recovery` / `_bind_guard`, per `test_delegated_identity`) stay honored.
- **Stage 4 (high) — `ConfirmationCoordinator` + `TurnStreamer`.** The HITL park/resume (SPEC-020/030/031) and the reply/SSE path. Planning re-confirmed the high-risk label: both monsters are async generators that arm ~13 contextvars *lazily inside the body* and reset them in a load-bearing `finally`, and `MODEL_CATALOG` is a second live `monkeypatch.setattr(runtime_kernel, …)` surface consumed inside `stream_events`. **Decision (operator, 2026-11-16): incremental extraction — one collaborator per gated commit.** The memo's earlier "do the Option-B in-place split first" note is *rejected* for these two methods: splitting an async generator into helpers fragments the contextvar set/reset spine and would *add* risk, so each monster moves wholesale (the contextvars travel with the body and stay identity-bound). Shared discipline per commit: wholesale move, lazy-resolve `MODEL_CATALOG` + the `runtime_kernel`-defined stream primitives through the module namespace at call time, route every sibling call back through the kernel, characterization gate + full agent-platform suite + `make verify`.
  - **Stage 4a — `TurnStreamer`. Done 2026-11-16.** `services/kernel_streaming.py` (`TurnStreamer`, owns no mutable state) takes the whole turn-streaming / reply cluster: `stream_events`, `reply_text`, `normalize_event`, `fallback_stream`, the `build_*_message` builders, `_finish_authorization_stream`, the SPEC-062 R-3 reveal-on-commit delivery buffers (`_flush_pending_deliveries` / `_drain_held_deliveries` / `_discard_burned_deliveries`) and `_drain_trace_queue`. `runtime_kernel.py` 2,645 → 2,119 LOC; adds `tests/test_kernel_stage4a_characterization.py` (14 pins, incl. a discriminating pin that fails closed if `MODEL_CATALOG` were imported module-level instead of lazily); suite 1,848 green. Byte-parity held via two subtleties: (a) the async-generator delegators (`stream_events`, `fallback_stream`) are plain `def` returning the collaborator's generator *directly* — a wrapper frame's `aclose()` would not propagate to the inner generator, so its `finally` (the ~13 contextvar resets) would leak on early close; (b) `from __future__ import annotations` in the collaborator, because `reply_text`'s `-> BlockingReply` annotation would otherwise raise `NameError` at class-definition time (`BlockingReply` is lazy-imported inside the body).
  - **Stage 4b — `ConfirmationCoordinator`. Done 2026-11-16.** `services/kernel_confirmations.py` (`ConfirmationCoordinator`, owns no mutable state — the parked entries live in `CONFIRMATION_REGISTRY`, the durable cards in `CONFIRMATION_RECORD_STORE`) takes the whole HITL park / resume / expire cluster: `_build_confirmation_frame`, `_extract_browser_element_map`, `_record_resolution`, `_confirmation_message`, `_tool_names_have_browser_write`, `_batch_has_browser_write`, `_record_flow_approval`, `resume_confirmation`, the `_resume_confirmation` monster and `expire_confirmation`. `runtime_kernel.py` 2,119 → 1,480 LOC; adds `tests/test_kernel_stage4b_characterization.py` (11 pins); suite 1,859 green. Same discipline as 4a, plus two cluster-specific subtleties: (a) `_resume_confirmation` resolves the `runtime_kernel`-defined stream primitives (`TERMINAL_STREAM_EVENTS`, `flush_prose_frames`) through the module namespace at call time — a discriminating pin patches `runtime_kernel.flush_prose_frames` and fails if the coordinator captured it module-level; (b) `_batch_has_browser_write`'s class-qualified `AgentKernel._tool_names_have_browser_write` staticmethod reference is retargeted to `ConfirmationCoordinator._…` (a `self.`-reroute would not reach it). `_resume_identities` / `_requester_for_turn` stay on the kernel as shared identity helpers (both are instance-patch surfaces — `test_kernel_middleware` — reached through route-back). A discriminating pin closes the resume generator after its first frame and asserts the inner `finally` still reset the owner-token contextvar and cleared the parked entry, proving the async-generator delegators return the inner generator directly. Twelve now-dead `runtime_kernel` imports were dropped; the three deliberate re-exports (`AGENT_STATE_STORE`, `MODEL_CATALOG`, `emit_audit_event`) stay.
  - Stage 4 is complete: `runtime_kernel.py` 2,645 → 1,480 LOC across 4a + 4b (the two monster async generators now live in collaborators, each behind a delegator that preserves its `aclosing` / `finally` contextvar spine).

## 6. Invariants that must not move

- `agent-stream-event` / `execution-request` / `execution-receipt` stay **byte-unchanged** — the cross-product contract invariant every recent SPEC held.
- The SPEC-074 agent-role axis stays **ready-but-inert**; no extraction may accidentally thread a non-`None` agent-role.
- **Contextvar propagation** across `await` boundaries (`DELEGATED_TOKEN`, `CURRENT_PROSE_REDACTOR`, `CURRENT_AUTHORIZATION_TURN`, `AGENT_ROLE`) is the principal hidden hazard when code moves into a collaborator; each stage must prove the contextvars still resolve identically.
